Documentation

agterm

A native macOS terminal with a deliberately small interface and a full control API.

Overview

agterm is intentionally opinionated: rather than scattering shells across tabs, it organizes them into named workspaces, each holding the sessions for one project or context. That hierarchy is the whole model, and there is nothing else to learn before it is useful.

Everything the model holds is also an object a script can address. Almost anything you can do by hand, agtermctl can do over a local socket, and every state it sets it reads back. That is what keeps a screen of concurrent coding agents in order, but nothing here is limited to agents: with nothing scripted at all it is a capable general-purpose terminal.

For the real terminal work — rendering, VT parsing, and shell I/O — agterm embeds Ghostty's engine (libghostty); everything above is agterm's own.

Install

Available now — Signed, notarized builds are published on the releases page. Install via Homebrew or the direct download below; building from source is optional.

Releases are signed and notarized for Apple Silicon (arm64) Macs running macOS 14 or later, so they open without any Gatekeeper workaround.

Homebrew

$ brew install --cask umputun/apps/agterm

The cask also installs the agtermctl command-line tool, so cask users shouldn't run the in-app installer as well.

Direct download

Download the latest .dmg from the releases page, open it, and drag agterm.app into /Applications.

Optional Help-menu installers

None are needed to use agterm as a terminal; each connects it to a wider workflow, and you can run any of them later. The first launch on a machine points them out in a welcome dialog, which offers the skill and the status hooks and never appears again.

  • ›Install Command Line Tool… puts the bundled agtermctl on your PATH (a symlink in /usr/local/bin) so you can script the app. When that directory is writable by you it links with no prompt; when it is root-owned, which is the case on a clean Apple Silicon Mac, macOS asks once for an administrator password. The Homebrew cask already installs it.
  • ›Install Agent Status Hooks… lets a coding agent (Claude Code, Codex, Pi, OpenCode, or others) report its state onto its session's row, so you can tell which of several running agents is active, blocked, or finished.
  • ›Install Agent Skill… teaches Claude Code or Codex how to drive agterm through agtermctl, so an agent inside a session can build its own layout, run overlays, and manage windows without you explaining the API. It also knows the cookbook, so you can ask it to list the available recipes, set one up for you, or read one for reference when a workflow is hard to get right. It drives the app through the CLI, so install that one too. The same skill is also published as a plugin from the repository — claude plugin marketplace add umputun/agterm then claude plugin install agterm@agterm, or the matching codex plugin commands. Use one route or the other, not both: a machine with two copies of the skill leaves it undefined which one the agent picks. Adding the marketplace clones this whole repository, which is an app rather than a skill library; both CLIs take --sparse on marketplace add to limit the checkout, and it has to cover the marketplace manifest as well as plugins/agterm.

Build from source

Requires macOS 14+, Xcode 26 with xcodegen on PATH (plus its Metal Toolchain), and Homebrew.

# build libghostty + stage resources (idempotent)
$ scripts/setup.sh
# generate the Xcode project, build Debug, launch
$ scripts/run.sh
# host-free unit tests, no Xcode needed
$ cd agtermCore && swift test

The app bundles the CLI, but it also lives in the agtermCore Swift package and builds standalone, without Xcode or libghostty:

$ cd agtermCore && swift build -c release
# binary at agtermCore/.build/release/agtermctl

Extend agterm

agterm ships a small set of features on purpose. A great many of the tools you might wish it shipped are one line in keymap.conf, and the line stays short because three pieces do the work: a command turns any shell line into a named action on a key chord, an overlay gives an interactive program its own temporary terminal over the session, and any CLI you already have fills that slot. agterm never needs to know what the program is.

So “does agterm have a file browser?” has no yes-or-no answer. You bind the file browser you like, in one line. The four steps below each add one building block.

You are not expected to write these by hand. Install the agent skill from Help ▸ Install Agent Skill… and ask the agent in your session for what you want; it knows the syntax, the command catalog, and the traps below. Step 4 shows exactly that. The three steps before it are not the long way round: they are what let you read the line the agent writes, change it later, and tell a working answer from a plausible one.

To edit the file yourself, open it with File ▸ Edit Keymap… and apply your changes with File ▸ Reload Keymap.

1. Act on the session you are in

# open the session's working directory in Finder command "Open in Finder" ctrl+a>o open "$AGT_SESSION_PWD"

Read the line left to right: command is the directive, the quoted text is the name shown in the Navigate ▸ Custom Commands palette, ctrl+a>o is the chord that fires it — Ctrl-A, then O — and everything after that is an ordinary shell line. The chord is optional: leave it out and the action exists in the palette only. Names are unique: a second command line with a name already taken is skipped with a diagnostic. For a mouse path, turn on the Custom commands title-bar button in Settings ▸ Interface: it lists the same commands with their chords in a popover, in the order of the file. Once there are more than five, the five you run most are grouped on top, still in file order; use changes only which commands sit in that group.

The building block is session context. Every custom command is handed the session it fired from — its directory, name, id, and current selection — as $AGT_* environment variables and as {AGT_*} tokens substituted into the line. That is what makes one binding work in every session instead of hard-coding a path.

2. Run an interactive program over the session

# the yazi file manager, floating over the session at 95% command "Yazi" ctrl+a>y agtermctl session overlay open 'zsh -lc yazi' --size-percent 95 --target "$AGT_SESSION_ID" --socket "$AGT_SOCKET"

The building block is the overlay. A custom command on its own runs detached with no terminal, which suits launching a GUI app but kills a TUI at once, since it has nothing to draw on. An overlay is a real terminal, so yazi, lazygit, htop and the rest behave normally in it. It opens in the session's own working directory, and it disappears when the program exits, leaving the shell underneath untouched.

Custom commands report failures through notification banners, subject to the notification setting. Add --error-hud before a command's shell body to also show a ten-second panel. It shows the command name, exit status or launch error, and the last usable stderr line when available. The panel defaults to the center of the whole session. A successful command shows nothing, and a program overlay keeps its slot. See Key Mapping for placement options.

Note zsh -lc rather than zsh -c. The program an overlay runs inherits agterm's own PATH, not your shell's, so a Homebrew binary needs a login shell to be found — or an absolute path. Skip it and the overlay flashes open and vanishes, because the binary was never found.

agtermctl is how the line asks for that terminal: it is agterm's own command-line tool, and opening an overlay is one thing it can do. Step 3 opens up the rest.

--target "$AGT_SESSION_ID" is worth understanding rather than copying. agtermctl does not act on agterm directly; it sends a request over a socket, and agterm resolves it on arrival. Without a target the request means “whichever session is selected when this lands”, which is normally the one you pressed the chord in — but not if you switched in between. The token pins it to the session that fired, so the overlay always opens where you asked for it.

3. Reach the rest of the app

# a second session in this directory, alongside this one, left in the background command "Session here" ctrl+a>n agtermctl session new --cwd "$AGT_SESSION_PWD" --workspace "$AGT_WORKSPACE_ID" --window "$AGT_WINDOW_ID" --no-select --socket "$AGT_SOCKET"

The building block is the control API. Overlays are one entry in a much larger catalog: the same agtermctl creates and renames sessions, splits panes, moves windows, opens the native picker or a question dialog, reads a session's text back, and posts notifications. Every state it sets it also reads back, which is what lets a script build a whole layout rather than fire a single action.

The extra flags are the same idea as --target above, applied to every axis this command can drift on. A bare session new lands in whichever window is frontmost and whichever workspace is current when the request arrives, and it selects the new session; the ids pin all three to where the chord was pressed, and --no-select leaves you where you were. Keymap lines never wrap, so this one is long: one directive is always one line.

Past a certain size the line becomes a script, and that is where the cookbook starts: pick a project from anywhere and open it in its own workspace, park a set of workspaces and bring them back later, or have each tab resume its own agent conversation after a restart. Those are not one-liners, and the recipes do not pretend otherwise.

4. Have the agent write it

This is the normal way to add things, not a shortcut for people who dislike config files. Install the agent skill from Help ▸ Install Agent Skill…, then ask the agent running in one of your sessions:

add a custom command that opens yazi in a 95% overlay, bound to ctrl+a then y

The skill carries the keymap syntax, the full command catalog, the context tokens, and the PATH rule, so the agent writes a working line instead of guessing at one. The skill is what makes the difference: an agent without it will still answer, plausibly and wrongly. It is shown last rather than first because the three steps above are what let you tell those two apart, and what let you change the line afterwards without asking again.

From here, Custom commands & keys has the full keymap syntax and the bindable actions, the command reference lists every agtermctl command with its arguments, and the cookbook collects worked recipes to copy and edit.

Workspaces & sessions

A session is one running shell with a name, a working directory, and its own scrollback — the unit you work in and the row you see in the sidebar. A workspace is a named group of sessions for one project or context. Sessions can move between workspaces while still running, keeping their shell and scrollback.

  • ›Two-level sidebar tree: workspaces, each containing sessions. Each row carries a leading kind icon — a filled folder for a workspace, an outlined terminal for a session.
  • ›Default session name is the basename of its working directory. Renaming pins a custom name; clearing it reverts.
  • ›Add workspaces and sessions, and toggle the workspace filter and the flagged view, from the four-icon bar at the bottom of the sidebar. Rename inline (double-click a row's name); a click on a workspace's icon folds it at once. Copy Name on a session or workspace row copies its name to the clipboard. Duplicate Session from a single session's context menu for a fresh shell in the same workspace, right after it, in its current directory — only the directory carries over. Shift-click and ⌘-click select multiple sessions for batch flag, close, move, and drag. Right-clicking inside the selection keeps the whole batch, so Flag, Tint, Close, and Move to act on all of it; right-clicking a row outside narrows the menu to that row. Dragged sessions keep running, shell and scrollback intact.
  • ›Companions keep related shells or programs next to a session: a log tail, a watcher, a second shell for the same task. A companion is an ordinary session pinned to its parent, listed right after it and indented under it in the tree; the parent's disclosure triangle folds them away, and a folded parent shows a small marker when a hidden companion is blocked, completed, or has unread notifications. New Companion in the session row's context menu, the Session menu, or the action palette opens a login shell in the parent's current directory; bind it with the new_companion action in keymap.conf. Duplicate as Companion beside it copies the session's split layout into a new companion and starts another copy of each pane's program in its directory (duplicate_companion); when a pane's program cannot be copied, nothing is created and a panel over the session names the pane. Convert to Companion turns a session you started on its own into one: a fresh shell takes its place in its directory, and the session moves under it still running, its own companions with it, and stays selected (convert_companion). It is available for any top-level session; one attached from another Mac is converted on that Mac, and its new parent attaches here. On a session attached from another Mac, New Companion and Duplicate as Companion ask that Mac to create the companion under its own session and attach it here; closing it here only detaches it. A page companion opened on such a session is that Mac's page, shown here through its own channel, and it stays there when you close it here. For attaching a session together with its companions, see Remote sessions. Companions reorder only among themselves, and moving the parent carries them. Closing a companion closes only it; closing the parent closes the group, and one Reopen Closed Item brings it all back. While a parent has companions, its shell exiting starts a fresh shell in the same directory instead of closing the session (one that exits again within 2 seconds closes the group), and a Mac viewing that session attaches to the new shell. Flat lists such as the ⌃P palette, the Ctrl-Tab switcher, the Dock menu and the Attach Remote picker label a companion parent › child; the tree, rename and Copy Name keep the bare name. From a script: agtermctl session new --parent active --command 'tail -f build.log' --name logs, with --wait to keep the output after it exits. A page companion shows an HTML page or URL instead of a shell, labelled with the file name or origin: agtermctl session overlay open --html report.html --companion. With --page in place of --companion the page opens as a top-level page session of its own, right after the target's group, and holds companions like any session; Convert to Companion works on it too. A page row's own window.close() closes it as ⌘W does, with the close confirmation and the undo, and the row comes back after a relaunch (see Restore & persistence).
  • ›Drag up to 20 folders from Finder onto the tree to open sessions there. A drop on a row lands in that row's workspace; a drop on empty sidebar space uses the current workspace, or the focused one when the workspace filter narrows the tree to exactly one. Collapsed workspaces spring open while hovering and close again on cancel. Reveal a session's focused-pane directory in Finder from its context menu; the item is greyed out when that directory no longer exists. Folder-picking panels (Open Directory… and the Settings directory choosers) open in the focused pane's directory, or in the directory already configured where there is one, falling back to your home directory.
  • ›Narrow a crowded sidebar two ways: flag sessions across workspaces into a working-set view (a flag is durable and survives a move), shown as one flat list or, with Settings ▸ General ▸ Flagged view layout set to Workspace tree, nested under their workspaces with the ones holding nothing flagged left out. Drag to reorder: the flat list keeps its own order per window, across workspaces, which next/previous session follows; in the workspace tree a drag moves sessions between workspaces as it does in the ordinary tree. A workspace row's Flag All Sessions flags every session in it at once, and reads Unflag All Sessions once they all are. View ▸ Edit Flagged Sessions… lists every session in the window, so Return or a click flags or unflags one without leaving the flagged view; the empty flagged view links to it. Or focus a set of workspaces to collapse the tree to just their sessions. Focus one workspace to zoom to it, or mark several from their row menus and apply the filter once with the sidebar's grid button — marking never narrows the tree on its own, and suspending the filter keeps the set for one click back. View ▸ Edit Focused Workspaces… marks and unmarks workspaces the same way as the flagged editor. Creating a workspace while the filter is on adds it to the set, and selecting a session outside the set suspends the filter rather than discarding it. The set is per-window and remembered across restarts. If narrowing the sidebar would hide the session you are working in, agterm moves you to the most recent session still on screen, unless the narrowing leaves nothing visible at all. The two are independent.

Open a directory without the CLI. Run open -a agterm <path>, or right-click a folder in Finder and choose Open With ▸ agterm: agterm adds a session in that directory to the last-active window. This works while agterm is running (its usual state); otherwise launch it first. To place the session precisely, use agtermctl session new --cwd <path>.

Terminals: split, scratch, quick, search, overlay

Split panes ⌘D / ⌘⇧D

A session can split into two shells side by side with ⌘D or top and bottom with ⌘⇧D. Both panes share one sidebar row: a split is one session with two terminals, not two sessions. Using the other shortcut transposes a shown split; using its current shortcut hides it without closing the second shell. The divider follows the current axis and remembers its position; drag it to resize the panes or double-click it to return to an even split. Close Split in the action palette tears the pane down whatever it is running. Swap Panes in View or the action palette exchanges the two live terminals without restarting them. Their primary/split roles move with their physical positions, focus follows its terminal, and the divider stays put. The same operation is available as agtermctl session swap, including while a split is hidden.

Quick terminal ⌃`

A single throwaway shell for the whole app, not tied to any session or window. It appears in a floating panel at 90% of whichever screen has focus, on the Space you are currently on, and opens in the active session's directory, sized to 90% of that screen up to a comfortable maximum. Settings ▸ Interface sets that size as a plain share of the screen instead, which is worth doing on a large display where the built-in maximum is the smaller of the two. Bind a system-wide chord with global-hotkey in keymap.conf and it summons agterm from any application. Press the key again, or click away, to dismiss it; hiding keeps its shell alive. A panel opened by agtermctl quick show stays put instead of closing on click-away, so a script can drive it. Not restored across launches.

Per-session scratch ⌘J

An extra shell belonging to one session, for a quick aside next to your main work. It covers the session full-screen and hides again without killing it. While it is up, ⌘D and the split button hide it rather than rearrange the panes beneath. Opens in the session's directory; not restored across launches.

In-terminal search ⌘F

A search bar at the top of the focused terminal highlights matches in live scrollback with an "N of M" counter. Enter steps forward, Shift-Enter back, Esc closes.

Overlay control API

Runs one program in a temporary terminal over a session and disappears when the program exits, leaving the session unchanged. Mostly driven from the control API to launch an interactive program (a diff viewer, a process monitor) — full-size, as a floating panel, or scoped to one split pane while the sibling pane stays live. The same slot also holds a HUD, a small passive panel carrying a message instead of a program, which leaves the session focused and typable underneath. ⇧⌘J hides a session's program and page overlays without closing them, and pressing it again brings them back; a hidden program keeps running. The View menu, the command palette, an optional title-bar button (Settings ▸ Interface) and agtermctl session overlay hide|show|toggle do the same. With --html the overlay shows a local HTML page instead, such as a report or chart an agent just generated, or with --url a web page such as a running dev server, under a strip naming the file or site, then the page's title dimmed, with a close button, a hide button while the title-bar hide-overlays button is enabled, and, with --navigation, back, forward, reload, open in browser, and Show in Finder for a file or Copy Link for a URL; ⌘W closes it like any overlay. A file page opened with --chromeless has no strip, so a dashboard fills its session or split pane like a native view; a web page may drop it too when served from 127.0.0.1, ::1 or localhost, and then loads frames from its own site only. ⌘+, ⌘− and ⌘0 zoom the page, and every later page opens at that zoom. A page runs no JavaScript of its own unless opened with --js, and one that does can close its own overlay with window.close(). A web page keeps cookies and logins only while it is open, unless opened with --persistent, which uses one saved store shared by these pages; agtermctl browser clear empties it. A login that goes through another site still fails. A link the page opens in your browser asks you first. Pages can match the terminal through the theme's --agterm-* CSS variables, and drive agterm themselves through the page bridge. See the agtermctl reference.

Terminal zoom ⇧⌘↩

Fills the whole window with one terminal surface — a pane, the scratch, or an overlay — hiding the sidebar and collapsing the title bar to a slim strip with the traffic lights, the window title, and an exit button (⌘W leaves zoom too). A view mode, not a layout change: exiting restores split ratios, focus, and visibility exactly as they were, and everything else keeps running behind it. Scripts can zoom any surface by id with agtermctl surface zoom, including the pane under a running overlay, which keeps running and returns when zoom exits. Distinct from macOS window zoom and full screen, which size the window itself.

Dashboard control API

Watch several agents or builds at once: sessions' live output in one grid overlaid on the window. The cell unit is a session+pane — a non-split session is one cell, a split session is two (its left and right panes), capped at nine cells. Each cell's name chip also reflects the session's agent status, filling with the status color and pulsing while it blinks, unless macOS Reduce Motion is enabled; the status color and text remain visible without the repeating animation. A pane covered by a full overlay or its own pane overlay shows a label in its cell instead of the terminal underneath: the page's file or origin with its title when it has one, or the program's command when available. It is view-only — no cell's terminal takes input; the arrow keys move a highlight, Enter (or a single mouse click on a cell) jumps into that session and focuses that exact pane, and Esc closes. Opened over the control channel with agtermctl dashboard <ids…>, or agtermctl dashboard --mru to fill it from the window's most-recently-used sessions instead of naming ids. An id may carry a :left/:right suffix to place one pane instead of the whole session — the same form tree --json reports in dashboardMembers — so agtermctl dashboard "$a:left" "$b:right" keeps the panes you did not ask for out of the nine-cell budget. The most-recently-used grid also has a built-in opener — ⌘⇧G (or Navigate ▸ Dashboard, the command palette's Dashboard, or the title-bar grid button) opens it auto-sized. Cell fonts size absolutely (--font-size) or scale to the grid (--auto-size). Mutually exclusive with terminal zoom.

Navigation

agterm is built to run from the keyboard. Every action has a shortcut and appears in the menus. Three fuzzy palettes (type to filter, arrows or Ctrl-J/Ctrl-K to move, Enter to run, Esc to dismiss) and a Ctrl-Tab MRU switcher cover the rest; a title-bar clock button opens the recent-session list with the mouse. Right-clicking agterm's Dock icon offers New Session, New Window, Quick Terminal, Dashboard, recent sessions, and sessions needing attention for the last-active window; those lists and actions stay scoped to that window even if another window comes forward while the menu is open, apart from New Window, which belongs to no existing window and stays available whatever the last-active one is doing. That same recently-used history decides where you land when you close the session you are in — agterm returns you to the session you were most recently working in, not to whichever row happens to sit next to the one that closed. The pick stays inside the closing session's workspace, and in the flagged view stays within the flagged set, while in the tree with the workspace filter applied it stays within the marked workspaces. It widens beyond the workspace only when the close leaves nothing there to return to, and beyond what is on screen only when that too is exhausted. If no recent session qualifies at all, it falls back to the adjacent row, kept inside the narrowed view while one is applied, and to the first session of another workspace when the closed session was the last one in its own.

An action the menus currently disable — Rename Session with no session open, Focus Workspace with no workspace — still appears in the action palette and still matches what you type, but is greyed out and does nothing when chosen, so the palette stays a complete index of what agterm can do rather than changing shape as state moves. Rows that would be meaningless are still omitted entirely (Delete Workspace with one workspace left, Focus Right Pane with no split).

Windows

A window is a top-level bundle of workspaces and sessions in its own on-screen macOS window, with its own sidebar and its own sessions — so "work" and "personal" can run as two separate windows at once, each with its own tree. Keep a library of windows, open one per screen, and create, rename, or delete them from the File menu (New Window ⌥⌘N) or the action palette. The set of windows open at quit reopens on the next launch, frames restored. Windows are also fully scriptable — agtermctl window can create, raise, move, resize, and minimize them, so a few lines of shell can give every window the same frame and park all but the one you are on, turning several windows into what feels like one that switches contents.

Remote sessions

Open a session that runs on another Mac in this sidebar, as a row marked remote, splits and companions included. Its programs keep running over there; this Mac shows them at its own window size. For sessions on a Linux host, see Remote server, which shows them in a remote window instead.

Set up the other Mac

  • agterm runs in Live sessions mode there (Restore), which keeps a live program behind each pane. A page session needs no live program.
  • agtermctl is installed there by the cask or Help ▸ Install Command Line Tool…. A Mac that only runs agterm has no CLI an ssh command can find.
  • Key-based ssh works without prompts. agterm runs ssh non-interactively, so a password or host-key prompt is a failure, not a question.

Check the connection the way agterm makes it:

ssh -o BatchMode=yes studio.local true

No output means agterm can reach the host. A password or host-key prompt means agterm fails the same way. agterm runs ssh from the app, which has the launch environment, not your shell's: an agent exported in .zshrc passes this check and still fails in agterm. Put IdentityAgent and key settings in ~/.ssh/config, which both read.

Attach a session

File ▸ Attach Remote… (the attach_remote action, ⌘⇧R by default) lists the Macs in remotes.conf:

# remotes.conf, in the config directory: destination [label]
studio.local          Studio
me@mini.lan           Mac mini
  • The destination is what ssh takes; the rest of the line is an optional picker label. Lines starting with # are comments.
  • With more than one Mac listed, the picker asks which, then shows that Mac's sessions. The one you choose attaches in the current window, with its companions when it is a top-level session.
  • A panel over the session reports the connection while it is made. A failure stays up for five seconds, over the new session when part of a group could not be attached.
  • The item is greyed out while the file is missing or empty. An unusable line or an unreadable file is reported in a notification.

From a script:

agtermctl zmx tree studio.local                       # window/workspace/name (split) [id] cwd, every open window
agtermctl zmx tree                                    # without a host: what this Mac offers, in the same shape
agtermctl zmx attach studio.local 7c1e…               # the id from that listing, not the name
agtermctl zmx attach studio.local 7c1e… --companions  # with its companions
agtermctl zmx attach studio.local 7c1e… --window "$win"  # into an open window (id from window list), not raised

# pick from the listing and attach the choice
s=$(agtermctl zmx tree studio.local --json \
  | jq '[.result.remote.sessions[] | {id, label: .name, subtitle: (.windowName + "/" + .workspaceName + " " + .cwd)}]' \
  | agtermctl pick --prompt "Attach which session?" | jq -r '.id // empty')
[ -n "$s" ] && agtermctl zmx attach studio.local "$s"

Without --window the session opens in the frontmost window.

What can be attached

  • Only a session whose every pane still has a live program is listed. The choice is checked again at attach time, so a session that ended in between fails instead of handing back a fresh shell wearing its name.
  • --companions attaches each companion under the session. If one cannot be attached, the rest stay and the command fails naming what is missing.
  • A terminal companion attached on its own joins its parent's group when exactly one row in the window is attached from that parent. Companions created over there later are not followed.
  • A page session is listed too: attaching it opens that Mac's page as a top-level row here. A page companion attaches only under the row attached from its parent, so the picker leaves it out.

The attached row

  • The title bar shows a cloud and the host; hide it with Settings ▸ Interface ▸ Remote host. The Ctrl-Tab switcher and the recent and attention lists mark the row the same way.
  • Closing the row ends only this Mac's connection, and the programs over there keep running. agtermctl session close --terminate ends the session on the other Mac too, and agtermctl zmx kill ends the targeted pane's program there.
  • A closed row joins File ▸ Open Recent under Remote Sessions. Reopening attaches again while the other Mac still lists the session, or has it reopen its own entry first. Reopen Closed Item (⌘Z) inside the other Mac's undo time undoes a terminate there.
  • An open row is saved and attached again at the next launch. If the other Mac no longer has the session, the row says it ended there.
  • agtermctl tree --json reports remoteHost and remoteSessionID on the row.

Who leads a pane

The program in a pane sees the window size of the one Mac that leads it.

  • Attaching takes the lead in every pane, so the session arrives at your size with nothing to press.
  • On the other Mac, those panes are covered with a note that they are in use elsewhere. A key press on the cover, or agtermctl session lead, takes the lead back and covers the pane here.
  • Scripts typing into a covered pane on the other Mac still work, and so do their screen reads: both go through the session, not the covered view.
  • Closing the session here uncovers the panes over there.
  • Both Macs need an agterm with this behavior; against an older one the session arrives at the other Mac's size until you type.
  • While another Mac leads at a different size, cursor and screen-text reads here can disagree with the program's layout. Automation that relies on them is unsupported in that state.

What follows the session to this Mac

Each terminal attach also opens a presentation stream back to the other Mac. Over it, this Mac mirrors:

Mirrored Detail
layout two remote panes follow the other Mac's split direction, hide and show, and swaps; a split opened there later attaches here into an empty split slot; a replica closed here stays closed
status clearing the row's status or badge here (typing, selecting, Clear Status) clears it there too, under that Mac's reset settings, when the status came from there; a status set on this Mac's row clears here only
session context a context set here wins over the mirrored one; clearing it here shows the other Mac's again
sidebar info line, notify notifications, HUD a timed HUD closes on this Mac's own count of the time left, so the two can close a moment apart

What stays local: local panes, the divider ratio and keyboard focus. A HUD or overlay opened by a program on this Mac is never replaced by a mirrored one. A terminal notification (OSC 9/777) is not mirrored: it already arrives in the pane's output and shows here once.

  • A page session uses its page channel instead and mirrors none of this.
  • The stream needs only agtermctl on the other Mac's ssh PATH. An agterm there from before context mirroring mirrors everything but the context; one too old for the stream reads unsupported and the attach still works.
  • agtermctl tree --json reports the stream as the row's presentation. connected means mirroring works; it says nothing about the panes' own ssh connections.
  • An older other Mac leaves the layout alone.

What runs on the other Mac

Commands that change the session run on the Mac it came from, and the result attaches here:

  • Duplicate Session, a new split and Close Split, Convert to Companion;
  • the scratch terminal, refused while the row is not connected or when the other Mac's agterm is too old to show its scratch;
  • agtermctl session restart, zmx kill and session restore; a session from agterm-server refuses session restore, since the server keeps every pane running.

When the other Mac gives no answer, the request is reported as unknown and is never sent again or done here.

Commands that only inherit the session's directory run here: a custom command, an overlay opened without --cwd, the quick terminal, and New Session set to open in the current directory. They start in the other Mac's reported directory when that path exists here, else in your home. A custom command still sees the reported path in $AGT_SESSION_PWD and the host in $AGT_SESSION_HOST (empty for a local session).

Questions, overlays and pages from the other Mac

The first attached Mac to ask presents the session while nobody else does; its row's presentation reads mode: presenter.

  • A question (ask) or program overlay that a program there opens is shown on the presenting Mac, where you are, while the other Mac follows another Mac's lead in that pane, or in every pane for one covering the whole session. Otherwise it stays over there, and one already open stays put when the lead changes.
  • The answer or exit status still reaches the program over there. A handed-over overlay's program runs once, on the other Mac, inside an ssh terminal this Mac opens for it.
  • If this Mac refuses a question, it goes back to the other Mac. An overlay this Mac cannot show fails rather than opening over there. Closing such an overlay from a script asks it to end, and its result says how it did.
  • A status sound follows the same condition, for the pane that set the status: it plays on the presenting Mac while another Mac leads that pane, with the presenting Mac's own blocked sound.

Pages follow the same condition and open on the presenting Mac:

  • A file page reads its files from the other Mac as needed, and its buttons and scripts act on the other Mac's session, so a page that answers its caller answers the program over there. Finder and browser are refused for it, since the file is not on this Mac.
  • A web page loads directly here; with --persistent it uses this Mac's saved browser storage. A localhost page names a server on the other Mac, so it loads through an ssh forward from this Mac; an agterm here too old to forward refuses it.
  • A picture, markdown or text page (--image, --markdown, --text) is fetched and built here. A markdown page follows its links to the other Mac's files (an older agterm here keeps them as text), and a picture opened without a size is sized for this screen, so an agent there can show you its screenshot. An agterm here too old for these pages refuses the open.
  • A log page follows the file over there. session overlay follow, search, wrap and changes from the other Mac act on the page here and answer as they would locally; what you do in the page's bar reads back there. An agterm here too old for live text pages refuses a log page, opens a clicked log as a plain page, and refuses those commands.
  • Closing the page from a script over there takes it down here; reloading asks this Mac to do it.

Clipboard

pbcopy on the other Mac fills that Mac's clipboard, not yours. agtermctl clipboard set sends the text through the pane, asking every terminal attached to it to set its clipboard, this Mac's included; each applies its own clipboard-write setting. It needs no terminal, so an agent's shell tool can use it.

When the connection drops

The presentation stream. Mirrored status, context and HUD clear here and return on reconnect. Retries run after 1, 2, 4, 8, 16, then 30 seconds, every 5 minutes after eight failures in a row, and never stop; waking the Mac or a network change retries at once. While it is down:

  • the row says so and names the host;
  • a notification raised over there is never shown here;
  • a handed-over question goes back to the other Mac, a finished overlay held open with --wait closes, and a running overlay keeps running until its program ends.

Close and reattach the session to retry by hand.

A pane's ssh connection. The pane keeps its last screen.

  • If ssh itself failed (exit 255, which a refused login also gives), a bar under the pane names the host and says it is reconnecting. agterm attaches again once the host answers, on the stream's schedule; any key, waking the Mac or a network change retries at once and restarts the schedule. ⌘W still closes the session.
  • While the host keeps refusing, a line along the pane's bottom edge shows what ssh said last, such as a changed host key or a rejected login.
  • When the host answers, the last screen is replaced before the new connection is up, so a link that drops again right away leaves an empty pane with only the bar.
  • The pane comes back without taking the lead: if the other Mac leads by then, it arrives covered. It also arrives covered while the other Mac still counts this Mac's dropped connection as leader, which clears once that connection times out.
  • Any other exit prints one line naming the host, session, pane and exit status, and waits for a key.
  • If the other Mac removes the session, its replica here closes without waiting for a key, even over a disconnect prompt. The last replica waits for its ssh to exit and may then close the row.

Keepalive. When your ssh config sets no ServerAliveInterval for the host, or sets 0, agterm adds ServerAliveInterval 5 and ServerAliveCountMax 2, so a dead connection is noticed within about 15 seconds. Set a large value to opt out. A connection that joins an existing ControlMaster ignores these; the master's settings decide.

Remote server

agterm-server runs agterm sessions on a Linux host, and a remote window on the Mac shows them over ssh. Every pane is a zmx daemon on the host and the server keeps the workspaces and sessions, so closing the Mac, losing the network or quitting agterm leaves every shell running, and the next connection finds them as they were.

Install

Install the server from the Mac with the app's own agtermctl. The host needs systemd with a user manager and logind for lingering, bash and tar whatever the login shell is, and zsh, fish or bash as the login shell; a password or host-key prompt is answered on the terminal you run it from.

agtermctl server install dev.example.com  # -p, -i, -J and -F pass to ssh

It asks the host for its architecture (aarch64 or x86_64), downloads the agterm-server release matching the app's version from GitHub, and refuses it unless its sha256 matches the one the app was built with. The install then puts the binaries, zmx and their resources in ~/.local/lib/agterm-server with links in ~/.local/bin, writes ~/.config/systemd/user/agterm-server.service only when it is absent, so later runs keep your edits, and starts or restarts the service. It also needs lingering, without which systemd stops the server and every pane at your last logout: when loginctl enable-linger is refused, the install stops before starting anything and prints the command an administrator runs. An upgrade is the same command. The new files replace the directory by rename and the service restarts, while every pane keeps running.

The install ends with agterm-server install-hooks, which installs the agent status hooks and the agterm skill for the host's user from the server's own files, pointed at the server's agtermctl. The Codex hooks need jq on the host; without it they are skipped and the install reports the hooks incomplete. Codex's hooks and skill go to a nonempty CODEX_HOME in the command's environment, a relative one resolved against its working directory, and to ~/.codex otherwise; a CODEX_HOME that does not exist is reported and skipped. OpenCode's plugin is installed only where its config directory exists, for the version opencode --version reports or the one --opencode v1|v2 names. Run it again on the host after installing an agent there.

On the host, agtermctl reaches the server with no flags. A plain ssh HOST agtermctl tree can miss it, because a non-login shell's PATH often lacks ~/.local/bin; the installer says when it does, and ~/.local/bin/agtermctl needs no PATH. A service edited to use another state directory also needs AGTERM_STATE_DIR set to it. agterm's own remote commands put ~/.local/bin on PATH themselves.

To skip the download, pass a tarball already on the Mac with --from FILE, such as one you fetched from the release page yourself; it must match the same sha256. The command exits 0 when the server is installed, 3 when it is installed but the agent hooks are incomplete, and 1 on failure. A development build has no release to install. From a checkout of this repository, scripts/setup-zmx-linux.sh stages the Linux artifacts once and scripts/install-server.sh HOST builds the server from the tree and installs it the same way; it needs Docker, the toolchain of a source build, and key-based ssh.

Open a remote window

File ▸ Open Remote Window… (the open_remote_window action, no default chord) offers the hosts in remotes.conf, the list Attach Remote… also reads, and opens the only one without asking. agtermctl window remote open HOST does the same and prints the window id; a window already showing that host is raised rather than opened twice. The sidebar is the server's catalog: creating, renaming, splitting, moving and closing sessions and workspaces happen on the server, while selection, focus, font size, split dividers and the window frame stay on this Mac.

What runs where

The host runs every shell, the scratch, overlay programs and the catalog itself. The Mac draws them and keeps the window, settings, theme, keymap, the quick terminal and custom command bodies. Whatever a session shows the user (an ask, a pick, a page, a HUD or an overlay) is drawn by the Mac presenting that session; with no Mac connected it is held on the host until one shows the session. Each host gets a pool of shared ssh connections with at most eight channels each, which keeps under the stock sshd limit of ten sessions per connection without changing the server.

A program on the host reads what the server keeps: agtermctl events and session wait follow the server's own event history, a session info line expires there, surface cursor reads the pane's screen, and zmx list and zmx screen cover the server's daemons. Flag and tint on the server's rows are kept by the server, so every Mac shows them. Clearing the server's status or a badge on the Mac (typing, selecting the row, Clear Status) clears it on the server under the Mac's default rules; a status set on the Mac's row is cleared there only.

Disconnects

When the connection drops, the window keeps its last sidebar and screens, marked Disconnected, and keeps trying. Selection and scrolling still work; anything that would change the server is disabled, never queued, and no local shell takes a session's place. A reconnect starts from a fresh snapshot of the catalog.

An action whose reply was lost is marked pending, then unknown. The window asks the server's receipt table what became of it as soon as it can and clears the mark, and never sends it again blindly; one the server no longer remembers stays unknown, listed in the connection strip. agtermctl window remote dismiss clears those marks, without undoing or resending anything.

An ask, a pick, a page or an overlay opened on the host while no Mac shows its session is held there and offered to the next Mac that does. Only an ask or a pick ends unanswered, at its --timeout when it has one; a page or an overlay job waits with no limit, the Mac it is offered to has a short time to claim it, and a claimed job never starts a second time. A server restart forgets everything still waiting, and the agtermctl call waiting on it fails. Notifications are shown live and never replayed.

Close, detach and terminate

Closing the remote window detaches it, and everything keeps running on the host. Closing a session, a group or a workspace in it asks first. Detach, the default, hides it on this Mac and leaves it running; Terminate ends it on the server and needs a live connection; Cancel keeps it. A server that keeps Recent Closed gives Terminate the undo grace a local close has, so Reopen Closed Item (⌘Z) brings it back for a few seconds, and while its window is frontmost File ▸ Open Recent and Reopen Last Closed Item read that server's list, which agtermctl recent list|open|clear --window W reaches from a script. An older server ends it with no undo. Running overlays close either way. File ▸ Detached Sessions… (detached_sessions) brings a detached session or workspace back, and agtermctl session detach|reattach and workspace detach|reattach do the same from a script.

A pane whose shell exits is handled on the host as it would be locally. When the server loses a session's last pane daemon, or cannot start its replacement, the row stays in the sidebar marked Ended on HOST, its scratch still running if it had one. Closing it needs no prompt while connected and with nothing in its group still running; Detached Sessions… lists an ended session only to remove its record. An unreachable host never marks a session Ended; it reads Disconnected.

Scratch, custom commands and pages

A remote session's scratch is a shell on the host. It is kept while hidden and across a closed window, and ends only with its own exit, the session's close, a server restart or a session scratch --command replacing it. Custom commands run on the Mac, with AGT_* tokens naming the server's session and host; an agtermctl call they make goes to agterm on the Mac, which sends the structural actions a remote row supports on to the server. A page at a loopback URL on the host, such as http://localhost:3000, opens through an ssh forward on a free local port kept for the page's life, and a failed forward shows as the page's error.

A page session or page companion made on the host (agtermctl session overlay open --page --html FILE, a path on the host, or --url) shows in the remote window as a page row, and the same command aimed at one of the window's rows makes one on the server. A page at the host's own loopback is refused there, since no Mac would reach it. Each Mac shows the row through a view of its own. While it has none the row shows why: waiting for the host, the host unreachable, or the page's connection ended, and it keeps retrying until the page shows; a refusal from the server stays shown, and detaching and reattaching the row tries again. Only closing the row on the server removes it, which closing its page from the Mac does. An older agterm on the Mac does not show page rows, and their companions appear there as top-level rows.

Notifications

A program in any session can raise a desktop notification (via OSC 9 / 777, or agtermctl notify). It surfaces as a macOS banner and an unseen-count badge on the sidebar row, and the workspace row shows the total of its sessions, collapsed or expanded; clicking the banner brings agterm forward and focuses the exact pane that raised it, and focusing a session or typing in it clears its badge (the Badge reset setting can limit typing to Enter or turn it off) — or clear it headlessly with agtermctl session seen so an orchestrator driving a session over the socket can acknowledge it without pulling focus (agtermctl tree --json reports each session's unseen count). Banners and count badges toggle independently in the Notifications settings, which also sets the Dock-icon bounce for a background notification (off, once, or until you focus agterm) and an optional notification sound (a system sound attached to each delivered banner; None by default, silenced by Do Not Disturb). For a coding agent that just needs to say it is waiting, agent status is usually the better fit.

Accessibility

Voice dictation tools that probe for a focused text field — MacWhisper and similar assistive apps — engage over the terminal: the on-screen pane advertises itself to the accessibility system as an editable text area, so a hold-to-dictate widget anchors to it and dictated text lands at the prompt. Text arrives at the cursor the same way typing does, and an insert carrying a newline, a tab, or any other control character goes in as a bracketed paste, so a program that accepts bracketed paste takes it as literal text instead of running the line or completing the word. That last part is the same caveat ⌘V carries: at a raw prompt with bracketed paste off, a trailing newline still submits and a tab still triggers completion.

Two limits are worth knowing. The scrollback is deliberately not mirrored, so the exposed pane reads to a screen reader as an empty text area named "Terminal" rather than as the terminal's contents — mirroring the grid is a separate, much larger piece of work. And because the terminal appends at the cursor with nothing to read back, a dictation tool that re-sends its whole transcription on every revision (rather than only the new words) will concatenate its drafts at the prompt; tools that insert incrementally, MacWhisper among them, are unaffected.

System Dictation inserts text through macOS text input, the same path used by the keyboard and input methods.

Custom commands & keys

agterm reads a user-editable, kitty-flavored keymap file at ~/.config/agterm/keymap.conf. It rebinds built-in menu shortcuts and defines custom shell commands bound to keys (and listed in the action palette). The file is optional — a commented starter is written on first launch, and the directory can be changed in Settings ▸ Key Mapping. Three verbs; blank lines and # comments are ignored.

# rebind a built-in to a chord (mods joined by +)
map cmd+shift+l   toggle_split
map ctrl+shift+k  command_palette

# or to several alternatives, joined by | with no spaces around it
map cmd+t|ctrl+a>t  toggle_scratch

# define custom commands ("name" shows in the palette; chord optional)
command "Open in Zed"  cmd+shift+e  open -a Zed {AGT_SESSION_PWD}
command "Lazygit"      ctrl+a>g     agtermctl session overlay open 'zsh -lc lazygit' --socket {AGT_SOCKET}
command "Deploy"               ./deploy.sh

# one system-wide chord that summons the quick terminal from any application
global-hotkey ctrl+opt+space

A chord is modifier words (ctrl, cmd, opt, shift) joined by + and a base key (a single character or tab/space/return/delete/left/right/up/down, or f1 through f20). A Shift-typed symbol is written shift+<base> (e.g. shift+/ for ?, shift+= for +) — the base key, not the shifted symbol. Custom commands may also use a leader sequence (ctrl+a>g), and their chord must start with a modifier or a function key. For example, f5 and f5>x are valid custom shortcuts. On Apple keyboards, hold Fn/Globe or enable standard function keys in System Settings to send F1-F12 instead of media keys.

global-hotkey takes exactly one chord and binds it system-wide: it summons the quick terminal while any application is frontmost, which no other binding here can do — the rest only fire while agterm has the keyboard. It needs a modifier unless it is a function key, takes no alternatives and no leader sequence, and a second global-hotkey line replaces the first. macOS registers it by physical key position, so it keeps firing on a non-Latin layout. Because the system owns it rather than agterm, it takes no part in the collision rules below. Note which side wins: the system-wide chord takes the key even while agterm is in front, so binding one a menu item already uses means that menu shortcut stops firing. It is unset unless you add the line: agterm ships no default because registering a chord takes it from every other application on the Mac, and that is not a cost to impose on someone who may never summon the panel from outside agterm. Spending it on the chord the in-app binding already uses is allowed and is the way to get one shortcut that works everywhere — global-hotkey ctrl+` makes ⌃` summon the panel from any application, at the price of that chord no longer reaching anything else. global-hotkey f5 similarly takes F5 machine-wide, including from local map and command bindings.

One binding can offer several alternatives, joined by | inside a single token with no spaces around it — map cmd+t|ctrl+a>t toggle_scratch fires the action from either, and a command takes alternatives the same way. For a built-in, the first single-chord alternative the menu can carry becomes the menu shortcut; every other alternative, on either verb, is delivered by a key monitor and must start with a modifier or a function key. This is also how a built-in gets a leader sequence, because a menu item holds exactly one key equivalent: map ctrl+a>s toggle_split binds the sequence and leaves the action with no menu shortcut at all — its shipped ⌘D is gone rather than kept, and free for another action to claim. A typo in one alternative rejects the whole line, so a mistake can't hide behind a line that half worked; an alternative that merely breaks a rule or collides with an existing binding drops on its own and its siblings keep firing. If a line ends up binding nothing at all, the action simply keeps the shortcut it shipped with.

A leader sequence fires once and forgets its prefix. Add --repeat after the chord, on either verb, to keep the prefix live until half a second after you release the key, like tmux's bind -r: with map cmd+opt+up|ctrl+a>ctrl+h --repeat previous_session and map cmd+opt+down|ctrl+a>ctrl+l --repeat next_session, ⌃A ⌃L ⌃L ⌃H walks two sessions down and one back, the shipped ⌘⌥↑/⌘⌥↓ still working, and holding the tail repeats it. Any other key ends the window and reaches the terminal as usual; only a leader sequence repeats. A tail without a modifier, like ctrl+a>n, takes that letter when you type it within half a second of releasing the previous one.

Chords are written in Latin and keep working on a non-Latin keyboard layout. A layout that cannot type ASCII — Russian, Greek, Hebrew, Arabic, Thai — resolves every chord by the physical key position, so cmd+o still fires on the key marked O even though it types щ. A layout that can type ASCII binds what it types, so an alternative Latin layout keeps its own letter positions: on Dvorak, cmd+o follows the O you actually type. A chord holding ⌘ binds what the layout types while ⌘ is held, as the menus do, so on Dvorak - QWERTY ⌘ cmd+d fires on the QWERTY D key.

Failure panels are opt-in per command. For example, command "Build" ctrl+a>b --error-hud ./build.sh shows failures at the center of the whole session. Add --error-position POS to choose a HUD position, or --error-pane left|right to select a pane role when the failure is reported. Positions are top-left, top-center, top-right, center-left, center, center-right, bottom-left, bottom-center, and bottom-right; top and bottom are aliases for the middle column. If the chosen pane is hidden or gone, the panel covers the whole session at the configured position. Only opted-in commands capture standard error for the panel.

Flags may appear in any order after the optional chord; for palette-only commands they follow the quoted name. Position and pane require --error-hud. A missing or invalid value, duplicate flag, unknown leading --error-* option, or empty shell body skips the command with a diagnostic. The first ordinary shell token ends option parsing, so --error-hud ./script --error-pane right passes the latter arguments to the script unchanged. Use -- to end options explicitly before a shell body starting with a reserved name. A chord is never parsed after flags.

The binding (⌃⌘F by default) is handled directly instead, which is why the menu entry advertises the system's Globe+F rather than your chord. Both work, and rebinding toggle_fullscreen changes the chord as usual — it just won't show up next to that menu item.

Command tokens

{AGT_SESSION_ID}   {AGT_SESSION_NAME}   {AGT_SESSION_PWD}   {AGT_SESSION_HOST}
{AGT_WORKSPACE_ID}   {AGT_WORKSPACE_NAME}
{AGT_WINDOW_ID}   {AGT_WINDOW_NAME}
{AGT_PANE}   {AGT_PANE_ID}   {AGT_SELECTION}   {AGT_SOCKET}

Tokens expand at fire time (also exported as $AGT_* env vars on the spawned process). A token is substituted raw into the shell line, so for content you don't control — {AGT_SELECTION}, and also {AGT_SESSION_NAME}/{AGT_SESSION_PWD} (a remote host can set these via OSC) — prefer the matching quoted env var, e.g. "$AGT_SELECTION". {AGT_PANE} names the pane's current role, left, right or scratch, and {AGT_PANE_ID} the same stable token that pane's shell holds as AGTERM_PANE_ID, so a command can keep addressing that terminal with --pane-id after a swap or a promotion has changed its role. A chord pressed inside an overlay carries the token of the pane underneath, the one the role names. It is empty for a launcher fired with no session.

Detached, no TTY — a custom command runs as a detached /bin/sh -c with no controlling terminal, so it suits fire-and-forget launches (GUI apps, scripts) — not interactive TUIs. Run a TUI like lazygit in an overlay (agtermctl session overlay open) or a scratch terminal, which have a real TTY. A non-zero exit or spawn failure posts a banner when notifications are enabled.
GUI PATH — a custom command resolves its binaries against the app's GUI PATH: the launchd default plus the bundled agtermctl, /usr/local/bin and /opt/homebrew/bin. A bare agtermctl or Homebrew binary works; anything else your shell profile adds does not, and fails with exit 127. Give it an absolute path or wrap the line in zsh -lc '…' — zsh -ilc '…' when that PATH comes from ~/.zshrc, which -lc does not read. The program an overlay or scratch terminal runs gets the app's own unwidened PATH and always needs one of those.

Open the file with File ▸ Edit Keymap… (or the ⌃⇧P palette): it opens in a 95% overlay running $VISUAL/$EDITOR (falling back to vi) and reloads on quit. Apply edits made elsewhere with File ▸ Reload Keymap or agtermctl keymap reload. A malformed line never discards the rest — it surfaces in the diagnostics list in Settings ▸ Key Mapping while the good lines still apply.

To check what is actually bound, agtermctl keymap list prints every built-in with the binds it resolved to (the menu shortcut first, then any alternatives, joined with |), the custom commands, each diagnostic in full, and the key equivalents the menu bar is really carrying. If a binding will not fire, compare the last two: an action whose chord no menu item holds is usually a menu problem, not a keymap one. Only the menu shortcut can appear there — an alternative never does, and neither do undo_close (⌘Z) and toggle_fullscreen (⌃⌘F), which a key monitor delivers rather than a menu item.

v1 limitations

  • ›A built-in's menu shortcut is single-chord only: a leader sequence binds through the key monitor instead, as an alternative, and so never shows next to its menu item.
  • ›A map line can't bind a bare, modifier-less arrow — a built-in rides an always-on menu key equivalent, so a bare arrow would swallow the key in the terminal, the palettes, the dashboard grid, and every text field; any modifier makes it bindable. The literal + and > can't be a bare key token (they are the separators), but those keys are bindable as shift+= and shift+.; only increase_font_size's default ⌘+ shows as a glyph because its stored form doesn't round-trip through the file.
  • ›The Ctrl-Tab MRU switcher and Ctrl-1/Ctrl-2 pane focus are not rebindable yet.
  • ›Shortcut hints are not written the same way for both verbs. A built-in shows macOS glyphs (⌘⇧E), with every alternative listed space-separated and a sequence's chords joined by > as in the file (⌘T ⌃A>T), in the palette and in the toolbar and sidebar tooltips alike. A command shows the raw kitty spelling you typed instead (cmd+shift+e), alternatives still joined by |.

Event hooks

A hook is a shell line agterm runs when a control event fires: an agent status change, a notification, a session created or closed, a split or scratch pane shown or hidden, or the sidebar tree changing. Nothing has to stay running to react. Hooks live in ~/.config/agterm/hooks.conf, beside keymap.conf; a commented starter is written on first launch, and File ▸ Edit Hooks… and File ▸ Reload Hooks (or agtermctl hooks reload) edit and apply it. One verb; blank lines and # comment lines are ignored.

# on <kind> <shell...> on status ~/.config/agterm/hooks/status.sh on session.closed echo "$(date +%T) closed $AGT_SESSION_ID" >> ~/.local/state/agterm/sessions.log on pane.scratch ~/.config/agterm/hooks/scratch-layout.sh on tree.changed ~/.config/agterm/hooks/sync-outline.sh on app.launched ~/.config/agterm/hooks/reopen-pages.sh

The redirection in the second line does not create its directory: mkdir -p ~/.local/state/agterm first. A status script that reacts to one status must exit 0 for the others, or every idle event reports a failure:

#!/bin/sh [ "$AGT_EVENT_STATUS" = blocked ] || exit 0 afplay /System/Library/Sounds/Glass.aiff & agtermctl notify "needs input" --target "$AGT_SESSION_ID" --socket "$AGT_SOCKET"
  • ›Kinds. status, notify, session.created, session.closed, session.selected, tree.changed, pane.split, pane.scratch and pane.focused, which names the split pane a session's selection settled on, with its paneID. The split and scratch kinds carry shown or hidden and fire only on a real change, closing a split or the scratch shell exiting included. remote.opened and remote.closed fire beside the created and closed edges of a local row created by zmx attach and carry its ssh destination as host and the origin's session id as remoteSessionID; they describe the row in the tree, not the ssh connection, so undo re-emits remote.opened. tree.changed also covers an overlay, page or HUD opening or closing, coalesced over 100 ms per window, so it says the tree moved and not what happened. app.launched fires once per app run, after this file is loaded and the control socket accepts connections, with the restored sessions already in the tree: the place to recreate what a relaunch does not restore, such as pages kept in overlays. A hook added by a later reload does not get that launch's event. The same kinds agtermctl events prints; a status event also carries previous, the status before the write, so a script sees the transition without keeping state.
  • ›Several lines per kind. Each line is its own hook with its own queue and child; they start together with no ordering between them. An identical kind and command twice is skipped with a diagnostic.
  • ›What the script gets. The event as one JSON object on stdin followed by a newline and end of file, the shape agtermctl events --json prints, plus AGT_EVENT_KIND, AGT_EVENT_STATUS, AGT_EVENT_HOST, AGT_SESSION_ID, AGT_WORKSPACE_ID, AGT_WINDOW_ID and AGT_SOCKET, each set explicitly and empty when the event has no such field. The line runs detached through /bin/sh -c in the app's working directory with the same widened PATH a custom command gets, so a bare agtermctl resolves; pass --socket "$AGT_SOCKET" so it reaches the instance that fired the hook.
  • ›One process per line at a time. While a hook's script runs, further events for that line queue in order, up to 256; past that the oldest is dropped and agtermctl hooks list shows the count. Nothing waits on a script: a slow or hung one holds only its own queue, and there is no timeout.
  • ›Failures. A non-zero exit, a script that could not be started, or an event that could not be handed to a running script posts one banner per hook until that hook next succeeds or the file is reloaded. A script that never reads stdin is fine; only its exit status counts. hooks list keeps the last failure.
  • ›Reload. A hook whose line is unchanged keeps its running script, queue and counters across a reload, comments and reordering included. A removed line accepts no more events and finishes its running script, which hooks list still shows marked retired until it exits.
  • ›Loops. A hook whose command emits another event of the kind it listens to triggers itself again. The queue bounds how many processes run; it does not detect the loop. session hud open under tree.changed is one, since opening replaces the panel and emits the kind again: open only when the tree shows no HUD and use session hud update otherwise.

Page bridge

A page shown with session overlay open --html can run any agterm command: read the tree, switch sessions, rename, set a status, or hand a value back to the script that opened it. These are pages you or your agents write, trusted like a program in an overlay, which can already run every command; a --url page gets none of this. A page that pastes in outside text, an issue body say, escapes it.

Tag a button or a form with data-agterm and the socket's command name. It works with the page's JavaScript off, because agterm's own script handles the tags. data-agterm-target is the target, data-agterm-args a JSON object of fixed arguments, and a form's named inputs add to it by their field name: a number input sends a number, a checkbox true or false, anything else a string. A name that would send two values is refused. data-agterm-into names an element that shows the reply as text, or the error. A button outside a form must be type="button".

<!-- switch sessions, rename this one, and the page's own controls --> <button type="button" data-agterm="session.select" data-agterm-target="3F2A">api</button> <form data-agterm="session.rename"><input name="name"><button>Rename</button></form> <button type="button" data-agterm="session.overlay.reload">Refresh</button> <button type="button" data-agterm="session.overlay.close">Done</button> <button type="button" data-agterm="window.list" data-agterm-into="#out">Windows</button><pre id="out"></pre>

What a page leaves out comes from where it sits: a command that addresses a session, left without a target, acts on the page's own session, a command that addresses one window acts on the page's window, and session.overlay.close, reload, resize, navigate and submit on the page itself. hide, show and toggle act on the page's pane, or on every overlay of its session for a page that covers the whole session. reload from a page re-reads the shown page. An explicit target, active or window is used as given. Global commands stay global, and window.go, like sidebar, steps from the frontmost window. Without JavaScript the rows above are what the file says when it was written; a live list, built from tree and redrawn on Refresh, needs --js, which also gives the page agterm.request(cmd, {target, args}). It returns a promise with the reply, or rejects with the error.

<!-- switcher.html, opened with --js --> <div id="list"></div> <script type="module"> const list = document.getElementById('list'); const {tree} = await agterm.request('tree'); for (const ws of tree.workspaces) for (const s of ws.sessions) { const row = list.appendChild(document.createElement('button')); row.textContent = `${ws.name} / ${s.name}`; row.onclick = () => agterm.request('session.select', {target: s.id}); } </script>

A page can also answer the script that opened it, like agtermctl pick. Open it with --block: the command waits, prints the outcome as JSON, and exits 0 with the submitted value, or 2 when the page closes unanswered.

choice=$(agtermctl session overlay open --html branches.html --block) || exit <!-- branches.html --> <button type="button" data-agterm="session.overlay.submit" data-agterm-args='{"value":"main"}'>main</button> <form data-agterm="session.overlay.submit"><input name="value" placeholder="other"></form>

Commands that stream or finish after their reply (zmx present, zmx reset and the overlay and page helpers) are refused from a page, and so are requests from a frame inside it. sidebar and sidebar mode act on the frontmost window, as over the socket. See the command reference for submit and result --page.

agtermctl

agtermctl drives agterm from scripts over a local socket: create and arrange workspaces and sessions, type into them, run actions, open overlays and dialogs, and poll an event feed for status and lifecycle changes. It does not stream terminal output. Every command, with arguments, results and errors, is in the Command reference.

Addressing

  • --target and --workspace take a session or workspace UUID, a unique prefix of it (git-style), or active. Never a name.
  • --target defaults to active, so the current session rarely needs naming.
  • For a session, active is the selected one. For a workspace, it is the one a new session lands in: a workspace you just created in the foreground, else the selected session's, else the last one.
  • A new workspace stays the target until the selection changes (to another session or to none), or until you delete it or hide it with the workspace filter. workspace select moves the target to the one you name, an empty one included. So session new right after workspace new lands in the new workspace.
  • --window addresses another window's tree; see Windows.

Output and exit codes

  • A mutating command normally prints the id it changed; a few print a count or a diagnostic instead.
  • Batch session close and session move take repeated --target and print how many sessions actually changed.
  • session close --undoable appends (undoable) or (not undoable) after ok or the count.
  • --json prints the raw response; --socket PATH overrides the socket.
  • Exit code 0 on success, non-zero on error.

Inside a session

A shell inside agterm gets these variables, so a script can drive its own window without hard-coded ids:

Variable Value
AGTERM_ENABLED set in every agterm shell
AGTERM_WINDOW_ID the window
AGTERM_WORKSPACE_ID the workspace the shell started in; not updated when the session moves (tree shows the current one)
AGTERM_SESSION_ID the session
AGTERM_SOCKET the live socket path
AGTERM_PANE the pane's role at spawn: left, right or scratch; not updated after a promotion or swap, unset in an overlay

Picker

agtermctl pick opens agterm's fuzzy picker over a list your script supplies and prints the choice as JSON.

printf '%s\n' staging production | agtermctl pick --prompt "Deploy where?"
agtermctl pick --allow-custom --query "$name" --prompt "Rename to" < /dev/null
id=$(printf '%s\n' alpha beta | agtermctl pick --no-block | jq -r '.id')
agtermctl pick result "$id"
agtermctl pick cancel "$id"
agtermctl tree --json | jq -r '.result.tree.pickPending // empty'

Input. Nonblank lines on stdin, or a JSON array of {id, label, subtitle?} objects, each optionally with status, statusColor and statusShape for a status glyph at the end of the row.

Option Effect
(none) blocks and prints the picked, custom or cancelled result as bare JSON
--no-block prints the picker id at once; read it later with pick result, end it with pick cancel
--query TEXT prefills the field and filters at once, ranked by match score
--select ID opens with that item highlighted and scrolled into view; a --query that filters it out leaves the first visible row highlighted
--allow-custom allows an empty item list, turning the picker into a text prompt; the custom row appears once the query is not blank
  • Typing matches labels only. A subtitle is shown but never searched, so warning text on one row cannot filter out its safer neighbor.
  • With an empty query the items keep your order, so without --select Return on open runs your first item.
  • A call with no items still reads stdin: redirect it (< /dev/null) or it blocks.
  • While the picker waits, tree reports its id as the top-level pickPending.

Question dialogs

agtermctl ask puts a question over a session and prints the answer as JSON.

agtermctl ask "Continue?" --button yes=Yes --button no=No --default no
agtermctl ask "Commit message" --input multiline --placeholder "subject, blank line, body"
# {"result":"answered","id":"ok","label":"OK","index":0,"text":"fix: ..."}

  --choice-subtitle 398="waits on you: review" --choice 395="PR #395"

Check the answer's id before acting: Yes and No both exit 0.

Result Exit code
answered (any button) 0
cancelled 2
escaped (Esc or ⌘W) 3

Where it appears

  • The default terminal style uses the session's theme, one pending question per session.
  • --pane right covers only that pane; the other pane and the rest of the window stay usable.
  • An explicit --target can name an unselected session; the question waits hidden until you select it.
  • --style gui uses native buttons in a window modal shared with pick. Terminal questions can be open beside it.

Keys

  • Buttons only: Tab and the arrows move the highlight, Return answers.
  • A text field has the keyboard as soon as it opens. Return answers a one-line field, ⌘Return a multiline one.
  • A list: Up and Down move, Space toggles.
  • Esc and ⌘W dismiss the question as escaped.

Forms

  • Buttons default to OK and Cancel; Cancel ends it like Esc, returning nothing.
  • Without --multiple a list is radio buttons and returns exactly one id.
  • --other "Something else" adds a free-form line after the items. Typing selects it, clearing deselects it, and while selected its text comes back as text beside selected. A radio list returns one id or that text, never both.

Overlays

An overlay runs a program over a session without disturbing the shell beneath.

agtermctl session overlay open "revdiff HEAD~3" --target 9f3c        # full, hides the shell beneath
agtermctl session overlay open "htop" --size-percent 70             # floating, framed, 70% of the pane
agtermctl session overlay open "revdiff HEAD~3" --size-percent 80 --background-color "#2a1a3a"
agtermctl session overlay open "revdiff HEAD~3" --size-percent 80 --target 9f3c --follow
agtermctl session overlay open "make test" --wait      # keep it open after exit
agtermctl session overlay open "make test" --block     # wait for exit, return its status
agtermctl session overlay resize --size-percent 60 --target 9f3c   # in place; the program keeps running
agtermctl session overlay resize --full --target 9f3c
agtermctl session overlay close --target 9f3c
agtermctl session overlay result                       # the last overlay's exit status
agtermctl session overlay open "revdiff HEAD~3" --target 9f3c --pane right   # cover one split pane
agtermctl session overlay copy --target 9f3c --pane right   # the selection made inside it
agtermctl session overlay text --target 9f3c --pane right   # its screen
Option Effect
--wait keeps a "press any key to close" prompt so you can read the final output
--block reports only the exit status; an overlay never captures stdout, so a TUI writes its own result file
--follow switches you to the target; without it the overlay opens there without changing the active session
resize --size-percent / --full / --width --height floating at a percent, back to full, or one floating axis in points
--pane left\|right covers one split pane (below)

agtermctl tree tags a session with an open overlay (overlay).

Reading an overlay. session overlay copy returns the selection made inside the overlay, session overlay text its screen as drawn, wrapped where it wrapped. session copy and session text read the pane underneath instead: a selection in the overlay reads there as no selection, and session text --pane right returns the shell under it. A chord already gets the selection of the pane it fired in, overlay included, as $AGT_SELECTION, so a custom command uses that. For a program's real output, read the file it writes.

Pane overlays (--pane left|right) cover one split pane and leave the other visible and usable, so an agent in the split can show a diff over its own pane without blanking the one you read.

  • Each pane can hold its own overlay at once, each with its own background color.
  • Always full-pane: --pane does not combine with --size-percent, and overlay resize takes no --pane.
  • A session without a split accepts --pane left.
  • A pane that is not on screen is refused with pane not visible. Hiding the split afterwards is fine: the program keeps running and returns with the split.
  • Over a session-wide program or page, a pane overlay draws on top; the session overlay keeps running out of sight and comes back when the pane overlay closes or hides, unless you hid it yourself.
  • close, result, copy and text take the same --pane. ⌘W dismisses the focused pane's overlay before it would close the session; one on the other pane is not in front of you, so ⌘W keeps its usual meaning there.
  • tree --json reports the covered panes as paneOverlays.
  • AGTERM_PANE is the spawn role and is not updated after a promotion or swap, so a long-running shell should not assume --pane "$AGTERM_PANE" still names its slot.

Message panel (HUD)

A HUD shows a message over a session while a script or agent works, so the session says what is happening instead of sitting silent. It is passive: the session keeps the keyboard, the terminal is neither dimmed nor blocked, and nothing waits for an answer.

agtermctl session hud "gathering options…" --spinner --detail "scanning branches" --target "$AGTERM_SESSION_ID"
agtermctl session hud update "ready" --detail "pick a branch" --target "$AGTERM_SESSION_ID"   # repaint in place
agtermctl session hud "deploy finished" --hide-after 10 --target "$AGTERM_SESSION_ID"
agtermctl session hud "deploying" --position top-right --size-percent 30
agtermctl session hud "working" --pane "$AGTERM_PANE" --pane-id "$AGTERM_PANE_ID" --target "$AGTERM_SESSION_ID"
agtermctl session hud "deploying" --text-color "#7ec07e" --background-color "#202020"
agtermctl session hud "**deploy api** [PR](https://example.com/pr)" --markdown --sticky \
  --no-frame --position top --size-percent 100          # a caption strip across the top
agtermctl session hud close --target "$AGTERM_SESSION_ID"

open is the default subcommand, so session hud "…" posts one.

Option Effect
--position one of nine anchors: top-left, top-center, top-right, center-left, center (default), center-right, bottom-left, bottom-center, bottom-right; bare top and bottom mean the middle column. Off center it keeps a margin from that edge
--sticky drops the edge margin and lets the width reach 100%
--no-frame drops the border and the blank rows above and below the text
--size-percent sets the width only: at most 80% of the pane, or 100% with --sticky off center
--pane, --pane-id sizes and anchors within one pane; --pane-id "$AGTERM_PANE_ID" follows the shell through swaps and promotion, with --pane "$AGTERM_PANE" as fallback
--text-color, --background-color the text's color and the panel's backing
--spinner, --spinner-style bar, braille, circle, blocks, dot (blinks) or none; a style turns the spinner on
--hide-after SECONDS takes the panel down by itself; without it the panel stays until closed
--markdown, --file, --font-size PT a small board (below)

Size. Width comes from the longest line and height from the number of lines, so a title and subtitle give a wide, short panel. A frameless panel is its rows plus 12 points of padding tall, one row more than its text at the default font and padding; a program meant to sit under a caption leaves that room.

Updates. update replaces the whole message, so --detail, --spinner, --text-color, --sticky, --no-frame, --pane and --pane-id must be repeated. It can switch the spinner style in place. --background-color and --font-size are read once when the panel opens and kept across updates, which is why update does not take them.

Markdown boards. --markdown renders headings, bold, lists, code blocks, quotes and tables, up to 4096 characters. A single newline inside a paragraph is a space; use list items, or end a line with two spaces, to keep rows apart. A board taller than the panel is clipped, the hidden rows shown as a dim … N more. A link shows its label underlined and opens on ⌘-click as it would in the terminal, the one click the panel takes; any other click reaches the terminal. --file reads the message from a file once per command, so push each change with update. --font-size PT gives the panel its own font size. A controller agent can keep a board in a corner of its session:

agtermctl session hud --file status.md --markdown --font-size 11 --position top-right
agtermctl session hud update --file status.md --markdown --position top-right

One slot. The HUD shares the overlay slot:

  • a second hud replaces the first, and session overlay open replaces a HUD;
  • a HUD over a running program is refused, because a message is replaceable and a program is not;
  • ⌘W or session overlay close takes it down;
  • session overlay result over a HUD errors, and overlay resize takes a percent but refuses --full.

Panes. Opening on a pane that is not shown is refused. Hiding that pane hides the panel without stopping it, showing the pane brings it back, and closing the pane closes it. A restart of agterm drops the panel, so a script posts it again.

tree --json reports the panel as the session's hud object, with a pane HUD's current role in hud.pane and overlay false beside it. There is no event; poll the tree.

Messages between panes

A program in one pane can leave a message for another pane without typing into its terminal, so nothing has to guess when the receiver is ready.

agtermctl msg send "build done" --to "$AGTERM_SESSION_ID:right"   # the split pane
agtermctl msg send --all "deploy starting"                        # every live pane but this one
agtermctl msg read                                                # oldest first; removes nothing
agtermctl msg ack ID                                              # remove what was handled
agtermctl msg read --ack --wait --timeout 60                      # wait for mail and take it
  • Every live pane has a mailbox; the receiver reads it when it chooses and acknowledges what it handled.
  • Run inside a pane, agtermctl msg acts as that pane through AGTERM_SESSION_ID and AGTERM_PANE_ID.
  • Mail lives in the running app only: closing or restarting the pane, closing its session, workspace or window, or quitting agterm drops it.
  • A full mailbox refuses that recipient alone.
  • On agterm-server the server's panes message each other the same way, and a Mac showing the server window sees their pending counts and message events. A local pane and a server pane cannot message each other yet.

Ghostty config

agterm builds its terminal config from four sources. Each one overrides the one before it:

  1. ghostty's defaults.
  2. ~/.config/ghostty/config, your global Ghostty config. Off by default, so a config written for the standalone Ghostty.app never silently changes agterm. Turn on Settings ▸ General ▸ Use my global Ghostty config to fold it in.
  3. <config dir>/ghostty.conf (default ~/.config/agterm/ghostty.conf). Always loaded, and read only by agterm.
  4. agterm's Settings, which win. They set font-family, font-size, theme, background-opacity, background-blur, mouse-scroll-multiplier and right-click-action; the last two are set even when their controls are at the defaults.

ghostty.conf

This is the place to customize the terminal. It sits next to keymap.conf and works the same way: a fully commented starter file is written on first launch, so a fresh one changes nothing.

  • Any ghostty terminal key goes here; the key reference lists them. A common one: macos-option-as-alt = true.
  • File ▸ Edit ghostty.conf… opens it in a 95% editor overlay, as Edit Keymap does.
  • File ▸ Reload Config or agtermctl config reload applies edits made elsewhere. A malformed line is skipped and the good ones still apply; the returned diagnostic count covers every config source.

Clipboard

Programs can read and write the macOS clipboard over OSC 52.

  • Reads ask first, since a read hands your clipboard to the program. A normal ⌘V paste never asks.
  • Writes go through, as in other terminals, so a remote tmux or vim yank reaches your clipboard. Set clipboard-write = ask or deny to gate them.
  • Each prompt offers Don't ask again this session.

Selecting text with the mouse copies it to a private selection clipboard, which a middle-click pastes; the system clipboard is left alone until ⌘C. Set copy-on-select = clipboard to put every selection on the system clipboard as well, or false to copy nothing on select.

Links

Hold ⌘ over a link to see where it goes, at the bottom-left of the pane: a link whose text says one thing and points elsewhere shows its real target, and a session link shows the session it selects. Ghostty's link-previews setting decides which links get it.

Web links. A ⌘-click opens an http or https link in your browser. With Settings ▸ General ▸ Open links in set to a Session overlay choice, or agtermctl browser links overlay, it opens in a web overlay over its session instead:

  • full size or at 95%, 75% or 50% (overlay, overlay95, overlay75, overlay50; browser is the default);
  • JavaScript on, navigation buttons, and agterm's saved browser store, so a login made there lasts. Nothing is taken from your browser;
  • the page may go on to other sites, and its strip always names the site shown.

With a Session overlay choice selected, outside a program that captures the mouse, ⌘⇧-click sends that one link to the browser; use Shift-click to extend a selection. In a program that captures the mouse, ⌘⇧-click is the ordinary link click and follows the setting.

The link still opens in the browser when it sits in a HUD, when a HUD is up on the session, when the terminal is zoomed, when the session already has an overlay, or in the quick terminal. So does a plain http link to anything but a local address (localhost, a .local name, an IP address), which the overlay could not load. One exception: a page an earlier click opened and you then hid with ⇧⌘J is replaced by the new link and shown.

Local files

A ⌘-click on a local path opens it over its session. The path can be plain output, such as /tmp/shot.png or ~/notes.md, or a file:// link of the kind ls --hyperlink, eza and many compilers print.

They run none of the file's script and hand a web link to the browser only after asking. Remote sessions. In a session attached from another Mac or in a remote window, a path names a file on that Mac or Linux host, so the click goes there; a scratch running there works the same way. Session links

A ⌘-click on an agterm://session/<id> link in a pane, split or scratch selects that session and raises its window, with no confirmation. Print one from a shell:

printf '\e]8;;agterm://session/%s\e\\%s\e]8;;\e\\\n' "$AGTERM_SESSION_ID" "back to this session"

In Claude Code markdown, [label](agterm://session/<id>) does the same, since Claude Code prints it as a link (OSC 8); while Claude Code captures the mouse, use ⌘⇧-click. In a session attached from another Mac the id is that Mac's, and the click selects the one row here showing it; it never attaches anything or acts there.

Nothing happens for an unknown or closed session; when the destination window is zoomed, has the dashboard open or a picker pending; for any other agterm:// form; on a ⌘⌥-click; or for a link in a HUD, the quick terminal or a program overlay.

Links in programs that use the mouse

While a program has mouse reporting on, such as tmux with mouse on or stock vim, ⌘-hover underlines nothing and ⌘-click opens nothing: links are detected only while reporting is off. Ghostty.app does the same, per program.

  • Hold Shift as well (⌘⇧-hover, ⌘⇧-click) to reach the link anyway, unless the program claimed Shift for itself. That click follows Open links in.
  • In ghostty.conf, mouse-shift-capture = never makes Shift always win, and mouse-reporting = false turns reporting off for every program.

Agent status

A coding agent running in a session can put its status on that session's sidebar row, so you can tell at a glance which of many agents needs you. The glyph sits just left of the notification badge on every session that is not idle.

State Glyph
active lavender-grey
blocked amber
completed green; a one-time completed flash clears once you visit the session
idle nothing

Colors and shapes

Every state draws a filled circle by default, so the color tells them apart. Settings ▸ Agent Status ▸ Colors and Shapes gives each state its own color and shape. A distinct shape per state adds a second signal, so the states stay apart at a glance from the corner of your eye and without depending on color.

Set it from a script

# the state is idle, active, completed or blocked
agtermctl session status active --target "$AGTERM_SESSION_ID"
agtermctl session status blocked --sound default --target "$AGTERM_SESSION_ID"
agtermctl session status completed --auto-reset --target "$AGTERM_SESSION_ID"
agtermctl session status blocked --color '#ff0000' --target "$AGTERM_SESSION_ID"
agtermctl session status blocked --shape triangle --target "$AGTERM_SESSION_ID"
agtermctl session status blocked --pane right --target "$AGTERM_SESSION_ID"
agtermctl session status idle --target "$AGTERM_SESSION_ID"       # clear it
Option Effect
--auto-reset clears the status the moment you visit the session
--blink adds an attention pulse. macOS Reduce Motion stops the repeating sidebar and dashboard animation and keeps the status; the pulse returns when Reduce Motion is off
--sound NAME plays a sound once: default, or a system sound such as Basso, Ping or Tink. To sound on every blocked prompt without touching the hooks, set Settings ▸ Agent Status ▸ Blocked sound
--color #rrggbb overrides the color for this call only; the next status set without it goes back to the configured color
--shape NAME overrides the shape the same way: circle, square, triangle, triangle-down, play, diamond, capsule, seal, star, bolt, bell or checkmark
--pane left\|right\|scratch records which pane set the status, the main pane by default (below)

agtermctl tree --json reports on each session:

  • status and statusPane, the pane that set it;
  • statusColor and statusShape, only while a per-call override is in effect;
  • statusChangedAt, epoch seconds of the last applied write. Every write counts, idle and a repeat of the same status included, and so do automatic and manual clears, so a script polling tree can tell how long ago the status was last written. It is absent before the first set and is not kept across a restart.

Which pane set it

  • A block set from a background pane survives typing in another pane.
  • When the status needs you (blocked or completed), selecting the session reveals and focuses the pane that set it (the split, or a hidden scratch) instead of the main pane. That covers every way of selecting it: auto-follow, attention navigation ⌃⌥↑/↓, plain session navigation, the command palettes, a Dock-menu session and a sidebar click. An active status keeps the current pane. agtermctl session go --to next-attention only steps the selection and does not move focus into the pane.
  • While a session is blocked, a status written from a different pane is refused unless it is another blocked. With an agent in each pane, one reporting its progress cannot erase the other's request for input. That holds for idle too, which the bundled agent hooks send on their own when an agent starts or finishes.
  • The pane that set the block changes it freely, typing into that pane clears it, and Clear Status in the sidebar row menu clears it from anywhere.

Clearing it

  • Typing into a blocked or completed session clears its status, on the first key by default. Settings ▸ Agent Status ▸ Status reset can move that to On Enter, so a reply you started and walked away from keeps the glyph until you send it; Esc or Ctrl-C still clears a blocked one, since cancelling the prompt answers it. Disabled leaves the status to the agent's next hook or Clear Status.
  • Esc or Ctrl-C interrupts an active session and clears its status, whatever the setting.
  • To come back to a session later, Mark for Attention in its row menu gives an idle session a completed status that stays when you visit it, so attention navigation stops on it again. It never replaces a live status; typing in the session's main pane, Clear Status or the agent's next update clears it as usual.

Finding the sessions that need you

Attention navigation (⌃⌥↑/↓) steps through blocked and completed sessions. Two settings under Settings ▸ Agent Status, both off by default, widen it:

  • Attention navigation includes active sessions stops on active sessions too, in the same sidebar order. Landing on one keeps the current pane.
  • Attention navigation crosses windows walks every open window, window by window in sidebar order, raising the window it lands in.

When the sidebar is hidden the glyphs go with it. The title-bar bell (Settings ▸ Notifications ▸ Show attention indicator, off by default) covers every open window: dimmed when nothing needs you, plain when a session is active or completed, filled amber when any is blocked.

  • Clicking it lists the sessions that are not idle across all open windows: blocked, then active, then completed, newest first within each. Hover to highlight, click to jump.
  • With more than one window open each row names its window, and picking a session in another window brings that window forward first.
  • A blocked or completed row reveals the pane that set its status; an active row keeps the current pane.

The same list opens as a searchable palette with ⌃⇧I, Navigate ▸ Go to Attention…, or Show Attention in the action palette. Right-clicking agterm's Dock icon shows the last-active window's list under Sessions Needing Attention, beside its recent sessions.

Auto-follow blocked sessions

With several agents running, a session that blocks is easy to miss. Settings ▸ Agent Status ▸ Auto-follow blocked sessions (Disabled by default, or 5 sec, 10 sec, 30 sec, 60 sec or 5 min idle) selects and focuses the oldest waiting blocked session once you have not typed or clicked for that long.

  • It works per window, across that window's workspaces.
  • It takes you to each block once. After you have been shown a block and moved on, even without replying, it does not pull you back; it walks the waiting blocks oldest first, then stays quiet. A session counts again only after it leaves blocked and enters it again.
  • While you stay on a blocked session, it does not jump.
  • Turn off Auto-follow away from a running session (on by default) to keep the selection where it is while the current session is active.

agtermctl tree --json reports the window's idleMs (milliseconds since your last input, live) and autoFollowMs (the timeout in milliseconds, omitted when Disabled). agtermctl window list --json reports autoFollowMs per window as of the last refresh, but not the live idleMs.

Session context

Status says how a session is going; context says what it is about: a short line shown in the title bar, such as the PR, the issue or the task in hand. It states lasting purpose rather than current activity, so it survives quit and relaunch, and only --clear removes it.

agtermctl session context "PR #517: restore reap ordering" --target "$AGTERM_SESSION_ID"
agtermctl session context --clear --target "$AGTERM_SESSION_ID"
  • In the Normal toolbar it takes the title bar's second line, in place of the working directory.
  • In Compact it follows the session and window names on the one row, and a long value is cut before the names are.
  • Settings ▸ Interface hides it without clearing it.
  • tree reports it as the session's context.

Session info

For current activity there is session info: one line under the session's sidebar row, such as the step an agent is on or how many tests have run.

agtermctl session info --markdown --hide-after 30 --target "$AGTERM_SESSION_ID" \
  '**3** agents ^[running](color: "green") ^[1 idle](dim: true)'
agtermctl session info --clear --target "$AGTERM_SESSION_ID"
  • --markdown allows bold, italic and code. ^[text](color: "green") colors a fragment with any named tint color (not a hex), and ^[text](dim: true) dims it.
  • Each set replaces the whole line. The line is never saved, so it is gone after a relaunch.
  • --hide-after SECONDS clears it by itself. Give a positive interval and repeat it on each refresh, so the line expires if the script stops.
  • Settings ▸ Interface ▸ Session info shows it Always (the default), only in the flagged view (Flagged), or never (Off). Hiding never clears it.
  • A session attached from another Mac shows that Mac's line too, unless one is set here.
  • tree reports info, infoMarkdown and infoHideAfter.

Row tint

A tint tells rows apart at a glance: red for production, green for development. Pick one from Tint in a session or workspace row menu: None or one of twelve colors (red, orange, yellow, green, blue, purple, gray, teal, pink, brown, indigo, mint) that follow light and dark mode. Then Show On chooses Icon, Name, or Icon and Name.

agtermctl session tint red --target "$AGTERM_SESSION_ID"
agtermctl session tint green --on icon,name --target "$AGTERM_SESSION_ID"
agtermctl workspace tint red
agtermctl session tint clear --target "$AGTERM_SESSION_ID"
  • A workspace tint colors only the workspace row, never the sessions in it.
  • With several rows selected, Show On is available only when every selected row is tinted.
  • A color picked for an untinted row starts on the last Show On choice made while the app runs, and Show On shows it checked.
  • The command palette offers Tint Session: Red through Tint Session: None for the active session.
  • Any other color is a #rrggbb hex through agtermctl. It stays the same in light and dark mode, and the Tint submenu shows it as a checked Custom entry.
  • session new --tint and workspace new --tint create a row already tinted. tree reports tint and tintOn.

A tint on a local row survives quit and relaunch; a duplicated session starts without one. On a session attached from another Mac the tint stays on this Mac: the row does not show the other Mac's tint, and a tint set here is saved with the row. A remote window's row shows the server's tint, which every Mac shares. On an older agterm, an emoji or a PROD or DEV word in the name gives a visible marker, at the cost of pinning the name: the row then no longer shows the live terminal title.

Where it writes

  • The scripts go to ~/.config/agterm/agent-status/, with the bundled agtermctl's absolute path baked in, so they work without the CLI on your PATH.
  • A marker-guarded line for the shell integration goes into ~/.zshrc, ~/.bashrc and ~/.config/fish/config.fish (fish only when that directory exists). Open a new terminal for it to take effect.
  • The Claude Code hooks are merged into ~/.claude/settings.json and the six Codex hooks into ~/.codex/config.toml. Before changing either, the installer saves a copy beside it with a .bak suffix.
  • Running it again upgrades agterm-managed integrations and otherwise changes nothing.

Claude Code

  • When Claude Code runs as a worker under another agent with a shell between them, as in a tool call, its hooks stay silent, so the status of the pane that started it is not overwritten.
  • A background subagent or workflow keeps the row working. Its activity lights an idle row but never replaces the main agent's status. While Claude Code (2.1.145 or later) reports one still running, Stop posts active instead of completed; completed comes from the Stop after the last one finishes.
  • Two gaps remain: the main agent's activity can replace a subagent's permission prompt, and when the key that answers that prompt leaves the block in place, the row stays blocked until the main agent's next event.
  • After upgrading, restart agterm and run the install again: a running older app ignores the subagent's --if-idle and applies the write.

Codex

  • A permission request is only a candidate, because it fires before Auto Review. The adapter keeps automatic decisions active and turns the row blocked only once a real approval or structured question appears in that pane.
  • On Stop, a final message that ends a sentence with ? reports blocked. This is a guess from the text: it ignores code in single and triple backticks, and a ? that stands alone, opens quoted text, or sits inside a word (as in a URL query string) does not count. Every other final message reports completed and auto-resets.
  • Run /hooks in Codex after installing or upgrading and approve the hooks. Codex runs changed command hooks only once they are approved, so until then they do nothing.

Both the skill and the hooks installers read CODEX_HOME as exported by your interactive login shell. A nonempty value selects the Codex directory, a relative path resolved against that shell's working directory. An unset or empty value, a shell that fails to start, unreadable output or a timeout falls back to ~/.codex. The selected directory must already exist: a missing custom directory is skipped, with nothing installed into ~/.codex instead. Whether OpenCode is installed does not affect this.

Pi

Pi work starts as active and settles as completed once retries and queued continuations finish. Pi has no permission or structured-question event, so blocked is never guessed from its replies. Restart Pi or run /reload after installing.

OpenCode

The installer runs opencode --version and installs the matching plugin. It finds OpenCode on your interactive login shell's PATH ($SHELL, or /bin/zsh when unset). If the version cannot be told, it asks you to choose v1 or v2, or to skip OpenCode. Nothing else is needed: no npm dependencies, no configuration edits. Restart OpenCode after installing.

v1 installs ~/.config/opencode/plugins/agterm-status.js. It serves OpenCode 1.x only; OpenCode 2 does not load 1.x plugins and shows no status with it.

OpenCode event Status
session.status busy or retry active
idle completed, only when no session is still busy, so a task subagent cannot complete a busy parent
permission or question prompt blocked
reply or reject active, once no other prompt is waiting
a turn-ending session.error for a session already busy blocked. The idle that follows the halt is ignored, and a clean sibling's idle cannot erase it. An abort is ignored. A context overflow waits for the next event: busy means compaction resumed, idle means the turn ended (blocked)
deprecated session.idle ignored, so it does not fire twice with session.status

v2 installs a plugin at ~/.config/opencode/plugins/agterm-v2/tui.js by default. It reports the selected OpenCode session and its descendants into the current pane, even when several clients share a server; background tabs, ancestors and sibling sessions are left out.

  • Running work, retries and recovering compaction are active. Pending permissions and questions are blocked until all are answered or cancelled.
  • Success or an interruption by you is completed, but only once the whole family is no longer busy. A failure that ends the work is blocked once the family stops, and stays blocked until the next run.
  • Switching sessions, reconnecting and unloading the plugin refresh or clear the status.
  • The directory comes from that shell's OPENCODE_CONFIG_DIR, then $XDG_CONFIG_HOME/opencode, then ~/.config/opencode. An empty OPENCODE_CONFIG_DIR skips v2 with a warning, and so does a shell configuration that cannot be read while ~/.config/opencode exists; without that directory OpenCode is skipped as not installed.

Re-run the installer after switching major versions. A v2 install removes the agterm-marked v1 plugin in its directory; a v1 install leaves the v2 plugin directory alone. A v1 file you own, or one that cannot be read, is kept and reported in the install result.

Add Codex hooks by hand

The installer never rewrites a ~/.codex/config.toml it does not own. If that file already defines its own [hooks…] entries, or is not valid TOML, it is left untouched and the install alert sends you here. With CODEX_HOME set, edit <CODEX_HOME>/config.toml instead.

Check the shape of your existing hooks first, since that is why the installer declined:

  • If every one is an [[hooks.…]] array-of-tables entry, appending is safe, including for events you already hook. A repeated [[…]] header adds an element, so both your hook and agterm's run.
  • An inline hooks = { … } table or a plain [hooks.SessionStart] table makes the file stop parsing once you append, since TOML allows neither extending a closed inline table nor redefining a value. Convert those entries to the array-of-tables form first.
  • Do not add a second command line inside an existing entry: a repeated key in one table breaks the file too.

Restore & persistence

When agterm opens again, your workspaces, sessions, splits, directories and font sizes come back. What happens to running programs depends on Settings ▸ General ▸ Restore sessions:

Mode Each pane comes back with
Fresh shells (default) a new shell in the saved directory
Re-run commands the command it was running at the last clean quit, started again
Live sessions the same program, still running

A new mode applies after agterm restarts. agtermctl restore mode reads or sets it.

Live sessions

Quit, update or relaunch agterm while shells, servers and agents keep running. Primary and split panes reconnect; the scratch terminal comes back hidden. Overlays and the quick terminal close with the app.

Requirements

  • A zsh or fish shell: your macOS login shell, or the ghostty command when it is an absolute zsh or fish path with only login or interactive flags (command = /opt/homebrew/bin/fish --login).
  • The ghostty command wins over the login shell. The last one counts, across ghostty.conf, the inherited global config and their config-file includes. Any other command is ignored in Live mode.
  • agterm's bundled session helper (zmx).

Without a supported shell or the bundled helper, agterm uses fresh shells and Settings says why. The shell is read at launch; running panes keep theirs until Reset Live Sessions.

Upgrade and switch modes

  • Upgrade: install the new version (brew upgrade --cask agterm), quit, reopen. Panes reconnect. agtermctl version shows the installed version when it differs from the running one.
  • Switch to Live: current shells end at the next clean quit. The first Live launch restarts their commands where it can; shell state is lost.
  • Switch away from Live: after a restart, every detached live program in this state directory ends. If Live is still selected but cannot run, they are kept for a later launch.

Quit, close, delete

You The live program
quit cleanly keeps running; agterm records each pane's command as a fallback
force quit, crash, SIGTERM keeps running; nothing recorded
close a window keeps running; File ▸ Open Window reconnects it
delete a session, split, workspace or window ends after the undo time

A program that is still running always reconnects. If it is gone (say, after a Mac restart), agterm starts the recorded command in a new live shell. The pane gets a fresh shell instead when:

  • nothing was recorded (force quit, crash, SIGTERM, power loss);
  • its window was closed before the quit;
  • the command is on the denylist or has a control character.

What a reconnected screen keeps

Text, full-screen programs and normal colors come back. Lost from before the reconnect:

  • inline images;
  • prompt marks (OSC 133), so prompt jumps start at the reconnect;
  • palette colors a program changed;
  • links on screen.

New output works normally.

Known limit: startup feature checks

A program may ask the terminal about features while it starts. In a new Live pane, these can go unanswered:

  • kitty keyboard protocol (richer keys);
  • XTVERSION (terminal name);
  • OSC 11 (background color, for light or dark themes).

The program then lacks the feature until it asks again. fish 4.9.3 asks for kitty keyboard and XTVERSION only at startup: if unanswered, never again in that shell. zsh asks nothing at startup.

Reset Live Sessions

Agterm ▸ Reset Live Sessions… restarts sessions that need it and reopens agterm with the same layout. The item appears only while Live sessions is both selected and running. It covers:

  • sessions created before session-host support: tools there ask for the microphone after every update;
  • sessions older than the latest Live update, so they pick up its changes;
  • sessions under an older build's or another login's session host, which can block local network access after an update. agterm asks such a host to stop at each launch; it stops once no session uses it.

The dialog shows how many sessions it resets. Their running work stops, and recorded commands restart where possible; agent conversations may need resuming by hand. Others are untouched. With banners on, a notification appears only when something went wrong: some sessions could not be reset (run it again for the rest), or the session list could not be read and nothing was reset. agtermctl zmx reset --force skips the dialog.

Microphone requests from panes created through the session host stay attributed to agterm across restarts (troubleshooting).

From the command line

These need agterm running: only the app knows a leftover program from a closed window's.

Command Does
agtermctl zmx list every live program and its pane; closed windows' panes show nothing attached, which is normal
agtermctl zmx screen prints one program's screen, even with its window closed
agtermctl zmx prune ends programs no pane claims; a terminal attached from outside at that moment may end too
agtermctl zmx kill ends one pane's program, even in no visible window, with everything attached; needs session, pane, --force
agtermctl zmx reset --force Reset Live Sessions without the dialog

After zmx kill a split closes; a primary hands its place to its split, or the session closes. No undo time; Reopen Last Closed Item or agtermctl recent open brings it back with a fresh shell.

agtermctl tree --json reports live panes: surfaces[].backedByZmx, and a session-level backedByZmx that is true when every primary and split pane is live. The sidebar has no mark for it. Full options: command reference.

Commands from scripts

In Live mode, agtermctl session new --command takes long commands fine. A surviving program reconnects without running it again; a gone one gets the usual fallback. The pane closes when the command ends, or keeps its output with --wait. A command that ends quickly can lose its output and show only agterm: session is gone.

Re-run commands

At each clean quit agterm records every pane's foreground command; the next launch starts it again as a new process, visible panes first, the rest gradually.

A pane gets a plain shell instead for:

  • a force quit or crash, unless agtermctl restore capture ran first (a capture is used for one launch only);
  • a control character in the command (it would be typed as an editing key);
  • bytes that are not valid UTF-8 (they would replay a different argument);
  • ! in a csh or tcsh pane (expanded as history even in quotes);
  • a program on the denylist.

Only a single program restores faithfully; pipelines and command chains may not.

Denylist

restore-denylist.conf lists programs that never re-run: one command name per line, matched on the file name. agterm writes a commented starter (tmux, screen, zellij) only when the file does not exist.

  • Location: next to keymap.conf and ghostty.conf, default ~/.config/agterm/.
  • Settings ▸ Key Mapping moves all three; with no folder set, AGTERM_STATE_DIR puts them in <state dir>/config.
  • Read at launch, so edits apply next time.

Pin a pane's command

agtermctl session restore pins the shell code a pane runs at launch. --none pins a plain shell, --clear removes the pin.

  • Applies every launch until cleared.
  • Wins over the recorded command and the session's --command; ignores the denylist.
  • Runs only in Re-run mode, but can be set in any mode.
  • Stored in the window's state file and shown by agtermctl tree: no secrets.

A SessionStart hook can rewrite it, for example so claude --resume … --fork-session resumes instead of forking.

Page sessions

Page sessions on this Mac come back in every mode, with their file or URL, flags and companions, and after Reopen Closed Item. A missing file or silent server leaves the row with the error and a Reload button.

  • A file page opened with --js gets full control of agterm (page bridge) at every launch and reopen, without asking. Open only pages, and scripts they load, that you trust. A restored --command only reruns in Re-run mode.
  • A URL page gets no bridge.
  • A page row from another Mac is saved as an attachment, without the page; that Mac sends it again at launch.

Working directory

Sessions reopen in their last directory if the shell reports it (OSC 7). Ghostty's shell integration does that for zsh, bash, fish and nu; otherwise the session reopens where it was created. Wrappers that replace your shell at startup (Amazon Q, Kiro, Fig) break it: fix.

The directory is saved on quit and on each session add, close, move, rename or select, so a crash loses only cds since then.

Older agterm versions

Saving settings in this version removes the old restoreRunningCommand key. An older agterm opening the same state directory then uses fresh shells.
