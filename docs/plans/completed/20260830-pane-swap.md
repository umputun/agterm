# Pane Swap

## Overview

Exchange a session's two panes: the terminals trade both screen position and model role, so the
terminal that was primary becomes the split and vice versa. Reachable from the control API, the CLI,
the command palette and the View menu.

Position and role move together deliberately. A view-only reorder would leave the public `left`/`right`
addressing disagreeing with what is physically left and right; a role-only swap would change what
`agtermctl tree` reports with nothing visible happening. Swapping both keeps addressing honest.

What a user gets: put the agent that has become the session's main work on the left, or reorder a pair
without closing and re-creating either shell.

## Decisions

Settled with Eugene before planning; a change here is a plan update, not an implementation choice.

- **Role and view swap together.** One operation.
- **Gate on `hasSplit`, not `isSplit`.** A hidden split owns two terminals and visibility does not limit a
  role operation. Matching every neighbouring pane operation, and keeping the command's success independent
  of transient UI state.
- **`splitFocused` toggles**, so the same terminal stays focused and, when hidden, stays maximized. The
  exchange becomes visible on re-show.
- **`splitRatio` does not invert.** Divider geometry belongs to the layout, not to the terminals.
- **Overlays, their exit codes, and pane-tagged status follow their terminal.**
- **No rejection while zoomed or in the dashboard.** Those hosts are made replacement-safe instead. A socket
  command whose success depends on transient UI state is a poor contract.
- **Works on any session with a split, whatever created it.** This is why paired creation identity is in
  scope: without it a swapped `--command` session restores the command on the wrong pane. Materializing the
  command into a restore pin was considered and rejected — an override forces `command: nil`, losing the
  exec path, close-on-exit and `--wait`.
- **No default keyboard shortcut**, therefore no new `BuiltinAction`. `Close Split` is the local precedent.
- **An unrealized pane is a readiness failure, not a policy gate.** The store primitive is synchronous and
  atomic: it refuses without mutating when either slot is nil. The app-side action polls briefly for both
  slots first, so the ordinary render race is invisible to callers and a timeout reads like `session.type`'s
  existing `session not realized`. This does not reintroduce the rejected transient-UI-state contract: zoom
  and the dashboard are representable states made correct, while a missing surface means there are not yet
  two objects to exchange.
- **`agtermCore` source compatibility is preserved.** The `agterm-linux` fork consumes it as a library, so
  no new hard requirement lands on `TerminalSurface` and the new `ControlActions` method carries a default.
- **A baked `AGTERM_PANE` is spawn-role and can be stale.** The child environment cannot be rewritten, so a
  swapped shell still reports the pane it was born in. This is not new — `SurfaceEnvironment.swift:7-11`
  records the same staleness after a promote plus re-split (#199) and `AGTERM_PANE_ID` is the existing cure.
  A swap makes it reachable more often, so the shipped Codex watcher is fixed to use the token rather than
  left wrong. Examples promising that `--pane "$AGTERM_PANE"` targets the caller stop being universally true.
- **Identity that cannot follow the terminal is cleared, not left pointing at the wrong one.** Delivered
  desktop notifications encode `.main`/`.split` in their identifier and cannot be rewritten without
  re-delivery, so a swap clears them for that session through the existing `clearDelivered`.

## Solution Overview

One auditable symmetric primitive on `AppStore` spells the pane pairing once and exchanges it: both surface
roles, both overlay slots, status tags, focus, and the persisted/pending command and restore state. It saves
once. No generic key-path descriptor table — that is over-engineering for a two-pane model.

Around that primitive sit three supporting changes: paired creation identity so a command session survives
the exchange, a pane-role capability so the live surfaces' roles and callbacks follow their new slots, and
replacement-safe hosting so every host re-mounts on its new occupant.

Hosting is the largest of the three and it is not a zoom problem. Four model slots take part in a swap — the
two pane surfaces and the two pane-overlay surfaces — and three HOST FAMILIES render them with fixed ids: the
ordinary deck's split pane (`WindowContentView+Detail.swift:192`), the two pane-overlay panels (`:284`), and
zoom's split plus its overlay slots (`WindowContentView+Zoom.swift:139-167`). The dashboard family already
folds resolved surface identity in and is the pattern the other three follow. Scratch and the session-wide
overlay do not swap and need no change.

One helper serves all three, and its contract is narrow on purpose: it returns ONLY a token naming the
resolved occupant (from `TerminalZoomSurface.surface(in:)`, `TerminalZoom.swift:34`). Each call site keeps
its own host/slot prefix and appends the token. It must not return a whole id, or deck, overlay and zoom
would share one view identity and couple slots that have nothing to do with each other.

Ordering rule: the primitive comes first because it is testable host-free, but NO public caller — control,
CLI, palette or menu — lands until every host is replacement-safe AND the dashboard is verified. A swap
reachable from the socket while a host still holds a stale NSView is a blank pane in front of the user. The
rule is enforced by a `Prerequisites:` line on each exposure task, not by task order alone.

`closePrimaryPane` is left alone in this plan. Rewriting it as "swap roles, then tear down the now-right
pane" is a tempting follow-up but its asymmetric command/search/layout cleanup is what makes it readable;
revisit only if the duplication proves real.

## Technical Details

**Pane pairing exchanged by the primitive**

| Primary | Split |
|---|---|
| `surface` | `splitSurface` |
| `currentCwd` (resolved with `initialCwd`) | `splitCwd` (resolved with `initialSplitCwd`) |
| `oscTitle` | `splitTitle` |
| `foregroundCommand` | `splitForegroundCommand` |
| `restoreCommand` | `splitRestoreCommand` |
| `pendingRestoreCommand` | `pendingSplitRestoreCommand` |
| `pendingForegroundCommand` | `pendingSplitForegroundCommand` |
| `initialCommand` | `splitInitialCommand` (new) |
| `commandWait` | `splitCommandWait` (new) |
| left pane overlay triple | right pane overlay triple |
| `agentIndicator.statusPane` `.left` | `agentIndicator.statusPane` `.right` |

`splitRatio`, `splitAxis` and `isSplit` are layout and stay put. `splitFocused` toggles. `initialCwd` is an
immutable seed and is not swapped; each side's cwd is materialized from its resolved fallback before the
exchange. `initialSplitCwd` is refreshed to the materialized `splitCwd` rather than swapped: it is the split
factory's spawn directory (`agtermApp.swift:410`), so leaving it stale would spawn a later-realized split in
the pre-swap right pane's directory.

`statusPane` is retagged directly, NOT through `setAgentIndicator`: that writer re-stamps `statusChangedAt`
and emits a `.status` event (`AppStore+Status.swift:14-36`), so routing the swap through it would re-sort the
attention list to newest and rewrite a wall-clock field callers compare against `ControlEvent.ts`. The status
itself, its colour and its timestamp are unchanged by a swap; only the pane tag moves.

**Command identity.** `splitInitialCommand`/`splitCommandWait` persist in `SessionSnapshot` and feed the
split surface factory through the same `CommandRestore.RestorePlan` exec path the primary uses, so a swapped
command pane closes on exit or holds with `--wait` exactly as before the swap. Restore pins remain a separate
override layer and swap unchanged, including a deliberate nil.

**Protocol.** `session.swap`, no arguments beyond target and window.

Read-back needs one addition. `ControlSessionNode.commandWait` is computed as
`session.initialCommand != nil && session.commandWait` (`AppStore.swift:298`), so a swap that moves the
command to the split side would silently drop an existing read-back. `splitCommandWait` joins
`ControlSessionNode` alongside it. The rest of the result is observable through the existing fields, and note
what those are: `tree` carries no `splitCwd`/`splitTitle`, so an end-to-end assertion is built from primary
`cwd`/`title` plus `foreground`/`splitForeground` and `restoreCommand`/`splitRestoreCommand`.
