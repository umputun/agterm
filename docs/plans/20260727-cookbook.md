# Cookbook: installable agtermctl recipes + the repo's first CONTRIBUTING.md

## Overview

Add `cookbook/` at the repo root: a collection of complete, installable `agtermctl` workflows, each in its own directory with a README and its scripts. Add the repo's first `CONTRIBUTING.md` at the root, plus `cookbook/CONTRIBUTING.md` for recipe submissions.

- **Today**: the only worked examples live in `agterm/Resources/agent-skill/examples.md` (38 sections). They teach an *agent* the command semantics, inline in prose, and ship inside the app bundle. There is nothing a *human* can copy, install and run. There is no `CONTRIBUTING.md` anywhere in the repo.

- **Why now**: this was asked for directly. In discussion #293 olfway closed with *"a small repository with scripts like these might be useful as a collection of practical recipes showing what can be done with agtermctl, as well as a source of ideas and inspiration for people building their own workflows."* Discussion #71 is already that, in the wrong place: @ssgreg posted a complete per-tab Claude Code resume function, @brusnigin posted the Codex variant, and neither is discoverable from the repo.
- **Framing it supports**: the answer given repeatedly in #293 is that a workflow which is not in the model is a script, not a feature request. That answer only holds if the scripts are somewhere findable.

**Explicitly out of scope**: no dedicated site page (a paragraph in `site/docs.html` only); no generator or YAML front-matter (the index is hand-written); no thinning of `examples.md`; no `CHANGELOG.md` edit (release-only); no Swift changes of any kind.

## Development Approach

- **Testing approach**: Regular. There is no compiled code here, so "tests" means static verification. The set below is what runs locally; **CI enforces a subset of it, not all of it** — the split is stated explicitly under Testing Strategy, because claiming CI covers everything would be false.
- **The verification set, run at the end of every task that touches `cookbook/`:**
  - `shellcheck` over every `.sh` — clean, zero findings.
  - **parse each script with the shell its own shebang names**, not a fixed one: `zsh -n` for `.zsh`, `bash -n` for a bash shebang, `sh -n` only for a genuine POSIX `#!/bin/sh`. A blanket `sh -n` over every `.sh` false-fails on a legitimate bashism under dash, so the parser must follow the shebang.
  - the mode-and-shebang check: every script has a shebang, and every script the setup instructions tell the reader to **execute** is committed with the executable bit. A valid script committed `0644` passes every other check here and then dies with "permission denied" on the reader's machine.
  - the index check, **both directions**: every `cookbook/*/` has a `README.md` and a row in `cookbook/README.md`, *and* every index row points at a directory that exists.
  - the template check: every recipe README carries all six headings.
  - the recipe audit (below) and the privacy sweep (below).
- **CRITICAL — parsing is not correctness. Every recipe needs a static audit against the real command surface.** `shellcheck` and `-n` prove a script is well-formed, not that it does the right thing: they accept a misspelled flag, a wrong `jq` path into the tree JSON, a target predicate that matches every session instead of one, and a command that did not exist in the minimum version the README claims. These recipes delete workspaces and close shells, so a well-formed wrong command is the expensive failure mode, and nothing may be executed to catch it. Before completing any recipe task, audit each recipe line by line against the sources of truth already in the repo: every command and flag against `agtermctlKit`/`ControlProtocol` and `agterm/Resources/agent-skill/reference.md`; every JSON field read by `jq` against the documented `tree` response shape; every claimed minimum version against `CHANGELOG.md` (read it, never edit it). **The keymap-only recipe gets this audit too** — it carries commands but no script file, so no shell tool looks at it at all.
- **CRITICAL — never execute a recipe.** Every script here drives a live agterm through `agtermctl`, and a bare `agtermctl` on PATH resolves to the deployed `~/Applications/agterm.app`, which is the maintainer's real terminal with live sessions. `agt-park.sh` deletes workspaces; `agt-win.sh` minimizes windows; `agt-only.sh` rewrites the sidebar filter. Verification is static parsing only. If a runtime check is ever genuinely needed, it goes against an isolated instance with an explicit `--socket /tmp/<name>.sock`, never the default.
- **CRITICAL — the privacy sweep is a required gate, not a nicety.** Two recipes are ported from the maintainer's live local config, which sits alongside entries that must never reach a public repo. Before marking any recipe task complete, sweep the whole `cookbook/` tree for: IP-address literals, `user@host` strings, any absolute path under a home directory, and any private service or project name carried over from the source config. **The concrete pattern list is deliberately not written down here** — this plan file is committed to a public repo, and recording the values in a denylist exposes them exactly as much as using them would. Derive the patterns from the source config at implementation time, keep them out of every committed file, and confirm the sweep returns nothing.
- Complete each task fully before the next. Keep this plan in sync (`[x]` immediately, ➕ new tasks, ⚠️ blockers).
- Work in an isolated git worktree; `git fetch origin master` **before** creating it so it forks the current remote tip.

## Testing Strategy

- **Unit tests**: not applicable — no compiled code is added or changed.
- **Static checks**: the verification set above. Each recipe task runs the whole set locally before completing. **CI enforces only part of it**, and the plan says which part rather than implying full coverage:
  - *enforced by the `cookbook` job*: the two-direction index check, the kebab-case directory-name check, the six-heading template check, the shebang half of the mode-and-shebang check, `shellcheck` over `.sh`, and `zsh -n` over `.zsh`.
  - *local-only, by design*: the privacy sweep, because its patterns are deliberately never committed (see the CRITICAL note above) — a CI job cannot hold them without republishing them. Also the **executable-bit** half of the mode-and-shebang check: whether a script is executed or sourced is per-recipe intent, not something a job can derive (see the Technical Details note).
  - *was local-only by cost, now enforced in CI*: `zsh -n`. The original call was that `zsh` is **not** on the `ubuntu-latest` image, so moving the check into CI costs an `apt-get` step plus a check step outside the six-fixture-verified block. Review overturned it: the three shipped `.zsh` recipes then had no syntax gate at all, and an outside contributor has no reason to have run `zsh -n` before opening a pull request, so a parse error would merge with the `cookbook` job green. A one-time apt install is cheap next to that. The step mirrors the `shellcheck` one and adds `-n1`, because `zsh -n` reads a single script per invocation.
  - *local-only, and not what CI does*: `bash -n`/`sh -n` per shebang. The `cookbook` job runs no `-n` parse at all; `.sh` files are covered in CI only insofar as `shellcheck` refuses to parse a broken script, which is a weaker guarantee than the local per-shebang parse.
  - *local-only, by nature*: the recipe audit against the command surface. It is a reading task, not a mechanical one.
- **e2e tests**: not applicable, and specifically excluded — the project's XCUITests drive the app, and no recipe may be executed against a live instance (see the CRITICAL note above).
- **Regression risk on Swift**: zero by construction. If any task finds itself editing a `.swift` file, the scope is wrong — stop and update this plan.

## Solution Overview

**Layout**

```
cookbook/
  README.md                 what the cookbook is + the index table
  CONTRIBUTING.md           recipe submission rules
  project-switcher/         README.md  agt-only.sh
  park-and-resume/          README.md  agt-park.sh  agt-resume.sh
  window-per-project/       README.md  agt-win.sh
  fzf-path-picker/          README.md  fzf-insert.zsh
  overlay-and-split/        README.md                    (keymap-only, no scripts)
  claude-session-resume/    README.md  claude-resume.zsh   (@ssgreg)
  codex-session-resume/     README.md  codex-resume.zsh    (@brusnigin)
CONTRIBUTING.md             project-wide, first one in the repo
```

**Key decisions and why**

- **Overlap with `examples.md` is allowed, not policed.** A cookbook recipe may be a fuller, installable version of an examples.md entry, cross-linked both ways. The skill installs offline to `~/.claude/skills/agterm/` and must stay self-contained, so it cannot thin out and link to GitHub.
- **Recipes are pinned snapshots, fixed reactively.** Each names the agterm version it was tested against. The cookbook is deliberately **not** added to CLAUDE.md's keep-in-sync surfaces — a control-API change carries no obligation to sweep it. The control API is additive in practice, so real breakage is rare, and the honest contract beats a per-feature tax that would quietly stop being paid.
- **Hand-written index with a CI guard.** At seven entries a generator is overhead; the failure mode worth defending against is a contributor adding a directory and forgetting the index row, and that is one grep.
- **Extension-by-shell.** `.sh` = POSIX/bash, must be shellcheck-clean. `.zsh` = zsh, not linted. **shellcheck has no zsh support**, so mixing them breaks CI on day one — which is why `fzf-insert.sh` is renamed to `.zsh` on the way in.
- **Flat index, no categories.** Seven entries.
- **Third-party recipes carry a read-before-you-run caution.** The collection accepts other people's scripts and they are reviewed before merge, but a reader runs them locally against his own sessions, and several are destructive by design. So the caution states all three parts together — contributions come from other people, every one is reviewed, read it before you run it — on `cookbook/README.md`, in the `README.md` section, and in the `site/docs.html` paragraph. It is normal practice stated plainly, not a disclaimer implying the collection is unsafe.

## Technical Details

**Recipe README template** (all six headings required, checked by CI):

```markdown
# <Title>

<one-line summary>

<optional byline: "Contributed by [@name](https://github.com/name), from [#71](link).">

## What it does
## Requirements
## Setup
## Usage
## How it works
## Limits
```

`Requirements` names the minimum agterm version tested against. `Limits` states destructive behavior in plain words when the recipe closes sessions, deletes workspaces or kills shells.

**Index row format** in `cookbook/README.md`:

```markdown
| recipe | what it does | needs |
|---|---|---|
| [project-switcher](project-switcher/) | show only one project's workspaces | 0.18.0, jq |
```

The CI check greps `cookbook/README.md` for `(<dirname>/)`, so the link target must keep the trailing slash.

**CI wiring** — add a second output and filter to the existing `changes` job, then a new job:

```yaml
  changes:
    outputs:
      swift: ${{ steps.filter.outputs.swift }}
      cookbook: ${{ steps.filter.outputs.cookbook }}
    # ... filters:
    #   cookbook:
    #     - "cookbook/**"

  cookbook:
    name: Cookbook checks
    needs: changes
    if: needs.changes.outputs.cookbook == 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: recipe layout, index and headings
        run: |
          fail=0

          # directory set vs index set, BOTH directions
          dirs=$(find cookbook -mindepth 1 -maxdepth 1 -type d -exec basename {} \; | sort)
          # links come ONLY from canonical table rows, so a link in prose, an html
          # comment or a fenced example cannot satisfy the check
          links=$(grep -E '^\|' cookbook/README.md 2>/dev/null \
                  | grep -oE '\]\([a-z0-9][a-z0-9-]*/\)' \
                  | sed -e 's/^](//' -e 's|/)$||' | sort -u || true)
          missing=$(comm -23 <(printf '%s\n' "$dirs") <(printf '%s\n' "$links"))
          stale=$(comm -13 <(printf '%s\n' "$dirs") <(printf '%s\n' "$links"))
          for n in $missing; do echo "::error::$n is missing from the index"; fail=1; done
          for n in $stale;   do echo "::error::index row '$n' points at no such directory"; fail=1; done

          for d in cookbook/*/; do
            [ -d "$d" ] || continue
            name=$(basename "$d")
            if printf '%s' "$name" | grep -qE '[^a-z0-9-]|--|^-|-$'; then
              echo "::error::$name is not kebab-case"; fail=1
            fi
            if [ ! -f "$d/README.md" ]; then
              echo "::error::$name has no README.md"; fail=1; continue
            fi
            for h in "## What it does" "## Requirements" "## Setup" \
                     "## Usage" "## How it works" "## Limits"; do
              if ! grep -qxF "$h" "$d/README.md"; then
                echo "::error::$name README is missing the '$h' heading"; fail=1
              fi
            done
          done

          # every script carries a shebang
          while IFS= read -r -d '' f; do
            if ! head -c 2 "$f" | grep -q '#!'; then
              echo "::error::$f has no shebang"; fail=1
            fi
          done < <(find cookbook -type f \( -name '*.sh' -o -name '*.zsh' \) -print0)

          exit $fail
      - name: shellcheck
        run: find cookbook -type f -name '*.sh' -print0 | xargs -0 -r shellcheck
```

The whole block above was run under `bash -eo pipefail` against six fixture trees before being written down. Notes on the parts that are load-bearing rather than decorative:

- **The `[ -d "$d" ] || continue` guard is required.** With no recipe subdirectories yet, `cookbook/*/` does not expand, `basename` yields `*`, and the check emits a bogus `::error::* has no README.md` and exits 1. That state is reached in this very plan — Task 3 lands the CI guard *before* Task 4 creates the first recipe. Verified both ways: guard absent, exit 1 with the bogus error; guard present, exit 0 on the skeleton and still exit 1 on a real missing index row.
- **The index check is two-directional and reads only table rows.** A one-directional `grep` for the link anywhere in the file passes on a link sitting in prose, an HTML comment or a fenced example, and never notices a stale row left behind by a deleted directory. Both false results were reproduced against the naive version and both are caught by the `comm`-based set comparison: a prose-plus-fenced-only link still reports *missing from the index*, and a row for a non-existent directory reports *points at no such directory*.
- **`shellcheck` takes `-print0 | xargs -0 -r`.** The earlier `files=$(find …)` form word-splits on whitespace in a filename and glob-expands. `xargs -r` also removes the empty-input problem entirely, so the `if [ -n "$files" ]` guard is no longer needed — worth recording that the old `&&` form was verified to fail the step when no `.sh` existed (exit 1 vs exit 0 for the `if` form), which is why the naive one-liner is wrong.
- **`grep -qxF` for headings**, so a heading must match the whole line exactly — a mention of `## Limits` inside a sentence does not satisfy it.
- **shellcheck is preinstalled on the `ubuntu-latest` image — verified in Task 3, no install step needed.** It is listed under `apt.cmd_packages` in `actions/runner-images`'s `images/ubuntu/toolsets/toolset-2404.json` and appears as `shellcheck 0.9.0-1` in the generated `Ubuntu2404-Readme.md`, and that repo's README maps `ubuntu-latest` to Ubuntu 24.04. `zsh` is in neither list, so the job installs it explicitly for the `zsh -n` step (added after review; it was local-only until then, see Testing Strategy).
- **Deliberately not in CI: the executable-bit check.** Whether a script is meant to be run or sourced is intent, not something a job can derive — the two `#71` recipes are zsh functions pasted into `.zshrc` and must *not* be executable, while `fzf-insert.zsh` must be. CI checks only that every script has a shebang; matching the mode to the recipe's own Setup instructions is a per-recipe local item in the verification set.

**Root CONTRIBUTING.md outline** (revdiff's structure, ralphex's AI section, agterm's specifics):

1. *Before you start* — first PR: open a Discussion and wait. Check it doesn't already exist (68 control commands, custom commands in `keymap.conf`, six Settings tabs; check `agtermctl --help`, README, agterm.com/docs, the bundled agent skill). Discussions for ideas and questions, Issues for concrete bugs or agreed features.
2. *Is it worth it?* — most users vs niche; **does it belong in agterm or upstream in ghostty** (agterm is a shell over libghostty, so rendering, terminal emulation, key handling and font bugs are upstream); scope creep (a terminal with a workspace→session sidebar, not a multiplexer or an IDE); code proportional to value.
3. *Development setup* — `scripts/setup.sh` once (builds libghostty from pinned upstream; needs Xcode 26, the zig 0.15 keg, a one-time Metal Toolchain download; takes minutes), then `make build` / `make test` / `make test-app` / `make lint`. All four green. `make lint` is `--strict`, so any warning fails.
4. *AI-assisted contributions* — ralphex's section retargeted: Swift 6 strict concurrency, `agtermCore` stays host-free (no GhosttyKit/AppKit/Metal/CoreGraphics), and **add focused coverage to the appropriate existing suite, creating a new test file only when that gives clearer ownership**. Keep "you must be able to explain every line; 'the AI wrote it' is not an acceptable answer".
   - **Do not write "one test file per source file".** That is a Go-project convention and this repo contradicts it: `AppStore.swift` is covered by five files (`AppStoreTests`, `AppStoreOrganizationTests`, `AppStoreNavigationTests`, `AppStoreFocusTests`, `AppStoreCloseReselectionTests`). Publishing a rule the codebase violates would send every contributor's first PR the wrong way.
5. *Adding a user-facing action* — the thing a contributor cannot guess: not done until drivable from the control socket (a `Command` case, a `ControlServer` arm, an `agtermctl` subcommand, round-trip tests) and reflected in the bundled agent skill and `site/commands.html`.
6. *Issues and PRs* — the mandatory what-is-the-problem / how-does-this-solve-it.
7. *Cookbook recipes* — three lines pointing at `cookbook/CONTRIBUTING.md`.

**Deliberately absent**: any file-length or line-count rule. `CLAUDE.md` forbids making a contributor refactor a pre-existing long file, so putting a size limit in front of contributors would invert the project's own review policy.

**`cookbook/CONTRIBUTING.md` outline**: ship a workflow you actually run, not a hypothetical; one kebab-case directory; the README template; index row in the same PR; `Requirements` pins the tested version and that pin is the contract (snapshots, fixed reactively, may be dropped if broken and unclaimed); `.sh` shellcheck-clean, `.zsh` unlinted so be careful; no personal absolute paths, private hosts, IPs, usernames or internal infrastructure names; `agtermctl` resolved through an overridable variable; destructive behavior stated under **Limits**; credit and link when porting someone else's work; contributions are MIT.
